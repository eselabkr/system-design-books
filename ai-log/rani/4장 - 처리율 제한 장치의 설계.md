
# 4장. 처리율 제한 장치의 설계

## AI 활용 기록

### 클라이언트, 서버
**추가 질문 이유:** 처리율 제한 장치를 고민하는 관점에서의 클라이언트 ↔ 서버 에 대한 개념 파악
- **클라이언트(Client):** 서버에 데이터나 서비스를 요청하는 프로그램 또는 장치.
- **서버(Server):** 클라이언트의 요청을 받아 데이터를 제공하거나 필요한 작업을 처리하는 프로그램 또는 장치.

* 클라이언트는 요청을 보내고 서버는 서비스를 제공함.

### 서비스, 트래픽 및 API
- **서비스(Service):** 사용자에게 특정 기능을 제공하는 시스템 또는 프로그램.
- **트래픽(Traffic):** 네트워크를 통해 주고받는 데이터의 양이나 요청의 흐름.
- **API:** 서로 다른 프로그램이 정해진 방식으로 기능이나 데이터를 요청하고 응답받을 수 있도록 하는 인터페이스.

* API = 기능과 데이터를 주고받기 위한 인터페이스

#### HTTP와 HTTPS의 차이
**추가 질문 이유:** 고객사 웹페이지 주소를 HTTP로 한 경우도 있고, HTTPS로 한 경우도 있었는데, 그걸 몰랐을때 웹페이지가 계속 접속 안되서 봤더니 https 여서 접속이 안된 경우가 있던 기억과 두 상세 개념들 파악 및 웹페이지 오픈할때 왜 차이가 있는지에 대한 예시 등을 알아보기 위한 목적
- **HTTP:** 클라이언트와 서버가 데이터를 주고받기 위한 통신 프로토콜. 기본적으로 데이터를 암호화하지 않으며 80번 포트를 사용한다.
- **HTTPS:** HTTP에 TLS 암호화를 적용하여 데이터를 안전하게 주고받는 통신 방식. 일반적으로 443번 포트를 사용한다.

#### SSL와 TLS의 차이
- **SSL/TLS:** 클라이언트와 서버 간 통신을 암호화하고 서버의 신원을 확인하는 데 사용하는 보안 프로토콜. 현재는 TLS를 사용한다.
- **SSL(Secure Sockets Layer):** 과거에 사용하던 암호화 프로토콜로, 보안 취약점으로 인해 현재는 사용이 권장되지 않는다.
- **TLS(Transport Layer Security):** SSL을 개선한 보안 프로토콜로, 현재 HTTPS 통신에 사용된다.

**HTTP와 HTTPS 접속 차이**

1. 사용자가 웹페이지 주소를 입력하면 브라우저가 서버에 연결을 요청한다.
2. HTTP는 일반적으로 80번 포트로 연결하여 데이터를 주고받는다.
3. HTTPS는 일반적으로 443번 포트로 연결하고 TLS 연결을 수립한 후 데이터를 주고받는다.
4. 서버가 특정 통신 방식만 지원하거나 포트 및 인증서 설정에 문제가 있다면 접속 오류가 발생할 수 있다.

* HTTP 암호화 X, HTTPS TLS 암호화
** 반대로 알고 있던건 아니였던 걸까, URL이 여러개라 기억이 안나서 기억나는것 하나만 다시 체크해보니 지금은 이런식으로 페이지가 뜬다.

### DoS 공격과 처리율 제한
- **DoS(Denial of Service):** 시스템에 과도한 요청을 보내거나 취약점을 악용하여 정상적인 서비스 제공을 방해하는 공격.
- **DDoS:** 여러 장치에서 동시에 공격하여 서비스 장애를 유발하는 분산 서비스 거부 공격.
- **처리율 제한:** 일정 시간 동안 허용되는 요청 수를 제한하여 과도한 요청으로부터 시스템을 보호

Denial = 부인, 거부, 부정

처리율 제한이 서버의 부하를 줄이고 서비스를 보호하지만 모든 DoS/DDoS 공격을 방어할 수 있는 것은 아님

### 분산형 처리율 제한
- 여러 서버가 공통된 요청 횟수 정보를 공유하여 동일한 제한 정책을 적용하는 방식.
ex) Redis : 서버 간 요청 횟수를 공유

# 높은 결함 감내성
- 일부 구성 요소에 장애가 발생해도 시스템이 계속 동작할 수 있는 능력.
- 서버 다중화, 데이터 복제, 장애 자동 전환 등을 활용하여 장애 영향을 최소화

**정리:** 분산형 처리율 제한은 여러 서버가 일관된 요청 제한 정책을 적용하도록 하며, 높은 결함 감내성은 일부 장애가 발생해도 서비스가 유지되도록 하는 특성이다.

### 429 에러
**추가 질문 이유:** 500, 404 등 다른 여러개는 보았지만 429는 아직 나온적 없고, 웹 페이지에서 나온다면 어떤상황에서 나오게 될지 궁금함.

**429 Too Many Requests:** 일정 시간 동안 허용된 요청 횟수를 초과했을 때 서버가 반환하는 HTTP 상태 코드.

**쇼핑몰 로그인 API (1분에 최대 5회 요청 제한)**
1. 사용자가 로그인 버튼을 1분 동안 5번 클릭한다.
2. 서버는 설정된 처리율 제한에 따라 5번의 요청을 허용한다.
3. 같은 제한 구간에서 6번째 로그인 요청이 발생하면 HTTP 429를 반환한다.
4. 사용자는 일시적으로 로그인을 시도할 수 없으며, 제한이 해제된 후 다시 요청할 수 있다.

#### 웹페이지에서 나타나는 방식
- 브라우저에 `429 Too Many Requests` 오류 화면이 표시될 수 있다.
- 웹페이지에서 별도로 처리한 경우 "요청이 너무 많습니다. 잠시 후 다시 시도해 주세요." 등의 안내 메시지가 나타날 수 있다.
- API 요청에서 발생한 경우 화면에는 오류가 표시되지 않고 개발자 도구(Network)에서 429 상태 코드를 확인할 수도 있다.

**정리:** HTTP 429는 서버 자체의 오류 X, 처리율 제한을 초과했을 때 발생하는 응답 코드. 웹페이지에서는 오류 화면이나 안내 메시지 등으로 나타날 수 있다. 

### API 게이트웨이
- **API 게이트웨이:** 클라이언트의 API 요청을 받아 적절한 서버로 전달하고 공통 기능을 처리하는 장치.
- **처리율 제한:** 일정 시간 동안 허용되는 요청 수를 제한
- **SSL/TLS 종단:** HTTPS 연결의 암호화를 해제하고 내부 서버로 전달
- **사용자 인증:** 요청한 사용자의 인증 정보를 확인
- **IP 허용 목록 관리:** 허용된 IP만 접근할 수 있도록 제한

* 클라이언트와 서버 사이에서 API 요청을 관리하는 역할

### 이동 윈도 카운터 알고리즘
**추가 질문 이유:** 책의 계산 예시에서 현재 요청은 3개이고 분당 7개까지 허용되므로 추가 요청이 가능하다고 생각했음. 또한 현재 시간대의 30%가 지났다면 70%는 아직 요청이 발생하지 않은 시간이라고 이해하여, 왜 이전 요청 수에 70%를 곱하고 현재 요청과 합산하여 6.5개로 계산하는지 이해가 되지 않음. 이로 인해 신규 요청이 제한되는 이유를 파악하기 위함.

- **이동 윈도 카운터:** 현재 시간대의 요청 수와 이전 시간대의 요청 수를 일정 비율로 합산하여 처리율 제한 여부를 판단하는 알고리즘.

**계산식**

현재 요청 수 + (이전 요청 수 × 겹치는 비율)

3 + (5 × 70%) = 6.5개

**계산 원리**
- 현재 1분의 30%가 지났다면 최근 1분에는 이전 시간대의 마지막 70%가 포함됨.
- 70%는 앞으로 남은 시간이 아니라 이전 시간대에서 현재 이동 윈도에 포함되는 시간의 비율
- 이전 시간대의 요청이 균등하게 발생했다고 가정하여 이전 요청 5개의 70%인 3.5개를 반영
- 현재 요청 3개와 이전 요청 추정치 3.5개를 합산하면 6.5개
- 새로운 요청이 들어오면 7.5개가 되어 분당 7개 제한을 초과하므로 거부됨.

* 현재 시간대에 요청이 3개만 발생했더라도 최근 1분을 기준으로 판단하기 때문에 이전 시간대의 요청도 포함하여 계산함.
* 실제 요청이 3.5개 발생한 것이 아니라 균등하게 분포했다고 가정한 추정치

### Redis, INCR, EXPIRE
- **Redis:** 메모리 기반 데이터 저장소로 빠른 데이터 읽기와 쓰기가 가능함.
- **INCR:** 저장된 숫자 값을 1 증가시키는 명령어
- **EXPIRE:** 저장된 데이터의 만료시간을 설정하는 명령어

* Redis를 활용하여 사용자별 요청 횟수를 저장하고 일정 시간이 지나면 초기화할 수 있음.
* INCR과 EXPIRE를 별도로 실행할 경우 중간에 장애가 발생할 수 있어 원자적 처리를 고려해야 함.

### Lyft와 설정 파일
- **Lyft:** 미국의 차량 호출 서비스 기업으로 Redis와 같은 기술이 아님.
- **설정 파일:** API별 요청 횟수, 제한 시간 등의 정책을 별도로 정의하는 파일

* 설정 파일을 통해 처리율 제한 정책을 코드와 분리하여 관리할 수 있음.

### 처리율 한도 초과 트래픽과 메시지 큐
- 처리율 제한을 초과한 요청은 HTTP 429를 반환하여 거부할 수 있음.
- 메시지 큐를 활용하면 처리할 작업을 보관하고 나중에 처리하는 것도 가능
- 메시지 큐는 특정 처리율 제한 알고리즘에만 적용되는 기능이 아님.
- 단, 거부된 요청이 자동으로 큐에 저장되는 것은 아니며 별도의 설계가 필요함.

* 처리율 제한은 요청을 거부하는 방식뿐 아니라 시스템 설계에 따라 작업을 보관하고 나중에 처리하도록 구성할 수도 있음.

### 처리율 제한 관련 HTTP 응답 헤더
- **X-RateLimit-Limit:** 일정 시간 동안 허용되는 최대 요청 수
- **X-RateLimit-Remaining:** 현재 남아 있는 요청 가능 횟수
- **Retry-After:** 다시 요청하기까지 기다려야 하는 시간

* 클라이언트가 요청 한도와 남은 요청 횟수, 재시도 시점을 파악하기 위한 정보
* 모든 API에서 반드시 제공하는 것은 아님.

※ 예시 이해 못해서 진행
→ Redis에 저장된 카운터가 3인 상태에서 두 스레드가 동시에 요청을 처리하면 각각 1씩 증가하므로 5가 되어야 한다고 생각했음. 하지만 책에서는 두 스레드가 동시에 값을 읽고 변경하면 최종 결과가 4가 될 수 있다고 설명하여, 왜 이런 문제가 발생하는지 이해하기 위함.

- **경쟁 조건:** 여러 작업이 동시에 같은 데이터에 접근하고 변경하면서 예상하지 못한 결과가 발생하는 문제.
- **병행성:** 여러 작업이 같은 시간대에 진행되는 특성.

**카운터가 3인 상태에서 두 스레드가 동시에 접근할 경우**

1. 스레드 A가 Redis에서 카운터 3을 읽음.
2. 스레드 B도 Redis에서 카운터 3을 읽음.
3. 스레드 A가 읽어온 값에 +1을 하여 4를 저장
4. 스레드 B도 자신이 읽어온 값 3에 +1을 하여 4를 저장

**결과**
- 예상 결과: 3 + 1 + 1 = 5
- 실제 결과: 4

두 스레드가 각각 Redis의 값을 직접 증가시키는 것이 아니라, 동일한 값 3을 읽어와 각자 계산한 결과 4를 덮어쓰기 때문에 한 번의 증가가 누락됨.

**해결 방법**
- **원자적 연산:** 여러 단계의 작업을 하나의 작업처럼 처리하여 중간에 다른 작업이 끼어들지 못하도록 하는 방식.
- **Redis INCR:** 값을 읽고 증가시키는 과정을 하나의 원자적 연산으로 처리하므로 동시에 요청이 발생해도 정상적으로 카운터가 증가함.

* 단순히 두 스레드가 동시에 실행되는 것이 문제가 아니라, 값을 읽고 수정하는 과정이 분리되어 있어 같은 값을 기준으로 덮어쓰기 때문에 발생하는 문제.
* Redis의 INCR 명령 자체는 원자적으로 실행되므로 위와 같은 카운터 증가 문제를 방지할 수 있음.
