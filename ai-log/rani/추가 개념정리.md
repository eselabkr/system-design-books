### 1. 가용성

**추가 질문 이유:** 가용률 99%, 장애시간 등으로 표현되어 있지만 가용성의 개념이 모호함.

- **가용성:** 사용자가 필요할 때 시스템을 정상적으로 이용할 수 있는 정도.
- **가용률:** 전체 측정 시간 중 시스템이 정상적으로 서비스를 제공한 시간의 비율.
- **장애시간:** 시스템을 정상적으로 이용할 수 없었던 시간.
- **고가용성:** 장애가 발생하더라도 서비스를 지속적으로 제공할 수 있도록 설계하는 것.

**가용률 계산식**

가용률(%) = (정상 운영 시간 / 전체 측정 시간) × 100

| 가용률 | 연간 장애 허용시간 |
| --- | --- |
| 99% | 약 3.65일 |
| 99.9% | 약 8.76시간 |
| 99.99% | 약 52.56분 |
| 99.999% | 약 5.26분 |

**가용성을 높이는 방법**
- **서버 다중화:** 서버 하나에 장애가 발생해도 다른 서버가 요청을 처리한다.
- **로드밸런서:** 정상적으로 동작하는 서버에 요청을 분산한다.
- **데이터베이스 복제:** 데이터베이스 장애에 대비하여 복제본을 유지한다.
- **장애 자동 전환:** 장애 발생 시 정상적인 서버로 자동 전환한다.

**핵심:** 가용성은 서비스가 정상적으로 제공되는 정도이며, 가용률이 높을수록 허용되는 장애시간이 줄어든다.

### 2. 데이터 볼륨

**추가 질문 이유:** 추가 개념 정리

**데이터 볼륨은 문맥에 따라 크게 두 가지 의미로 사용된다.**

1. **저장 공간:** 데이터를 저장하기 위한 물리적 또는 논리적 공간.
2. **데이터 양:** 시스템에서 저장하거나 처리하는 데이터의 전체 크기.

- 시스템 설계에서 데이터 볼륨은 주로 처리하거나 저장해야 하는 데이터의 양을 의미한다.
- 데이터 증가량을 추정하여 필요한 저장소 용량과 확장 방향을 결정할 수 있다.

**핵심:** 데이터 볼륨은 데이터의 전체 양 또는 저장 공간을 의미하며, 시스템의 저장소 요구량을 추정하는 데 활용된다.

### 3. 응답 지연시간

**추가 질문 이유:** 메모리가 디스크보다 빠르고, 압축을 활용하면 전송시간을 줄일 수 있다는 설명은 있지만 그 이유가 명확하지 않음. 또한 동일 데이터 센터 내부 통신과 CA-네덜란드 간 통신의 차이 및 실제 사용 사례를 이해하기 위함.

#### 메모리와 디스크의 속도 차이

- **메모리(RAM):** 전자적으로 데이터에 접근하기 때문에 지연시간이 짧다.
- **HDD:** 데이터를 읽기 위해 디스크 헤드를 이동시키고 회전을 기다리는 과정이 발생한다.
- **SSD:** 기계적인 헤드 이동은 없지만 일반적으로 RAM보다 접근 지연시간이 길다.
- **디스크 탐색:** HDD에서 데이터를 읽기 위해 헤드를 원하는 위치로 이동시키는 동작.

#### 데이터 압축

- 데이터 압축은 전송해야 하는 데이터의 크기를 줄이는 과정이다.
- 압축과 해제에도 처리시간이 필요하지만, 데이터 전송량이 줄어들어 전체 응답시간이 단축될 수 있다.
- 대표적인 압축 알고리즘으로 LZ4, Snappy, gzip 등이 있다.
- 압축이 항상 빠른 것은 아니며 압축률, 처리시간, 네트워크 속도에 따라 효율이 달라진다.

#### 데이터 센터 간 지연시간

- **동일 데이터 센터:** 같은 시설 내부의 서버들이 내부 네트워크를 통해 통신하므로 상대적으로 지연시간이 짧다.
- **서로 다른 데이터 센터:** 물리적인 거리와 네트워크 경로에 따라 지연시간이 증가한다.
- **CA(캘리포니아) ↔ 네덜란드:** 서로 다른 대륙에 위치한 지점 간의 통신을 비교한 것으로, 데이터 센터 간 장거리 통신의 지연시간을 이해하는 예시로 볼 수 있다.
- 같은 지역에 위치하더라도 서로 다른 데이터 센터라면 네트워크 경로에 따라 지연시간이 달라질 수 있다.

**동일 데이터 센터 내부 통신과 데이터 센터 간 통신의 차이**

1. **동일 데이터 센터 내부**
   - 같은 데이터 센터에 있는 웹 서버와 데이터베이스 서버가 데이터를 주고받는 경우.
   - 예시: 웹 서버가 같은 데이터 센터의 DB 서버에 사용자 정보를 요청하는 상황.
   - 물리적 거리가 짧고 내부 네트워크를 사용하므로 일반적으로 지연시간이 짧다.

2. **서로 다른 데이터 센터 간 통신**
   - 서로 다른 지역에 위치한 서버들이 데이터를 주고받는 경우.
   - 예시: 미국 데이터 센터의 데이터를 유럽 데이터 센터로 복제하는 상황.
   - 장거리 네트워크를 거쳐야 하므로 일반적으로 지연시간이 증가한다.

**핵심:** 메모리와 디스크는 데이터 접근 방식에 따라 속도 차이가 발생한다. 압축은 전송량을 줄여 지연시간을 개선할 수 있으며, 데이터 센터 간 통신은 물리적인 거리와 네트워크 경로에 따라 지연시간이 달라진다.

### 4. 메시지 큐

**추가 질문 이유:** 이전 장에서 정리한 메시지 큐의 기본 개념은 이해했지만, 실제 메시지의 전달 과정과 비동기 처리 방식 및 사용 목적을 추가로 이해하기 위함.

#### 기존 정리 내용

메시지 큐는 처리할 작업을 바로 실행하지 않고 큐에 저장해두었다가 처리하는 방식이다.

메시지를 보내는 쪽과 처리하는 쪽을 분리할 수 있어서 비동기 작업에 사용할 수 있고, 각 서비스가 직접 연결되는 것을 줄일 수 있다.

#### 추가 개념

- **생산자:** 메시지를 생성하여 큐에 전달하는 시스템.
- **메시지 큐:** 전달받은 메시지를 보관하고 소비자가 처리할 수 있도록 하는 구조.
- **소비자:** 큐에서 메시지를 가져와 실제 작업을 처리하는 시스템.
- **비동기 처리:** 요청한 작업이 완료될 때까지 기다리지 않고 다른 작업을 진행하는 방식.

**동작 과정 (회원가입 후 이메일 발송 예시)**

1. 사용자가 회원가입을 요청한다.
2. 웹 서버가 회원가입을 처리하고 이메일 발송 작업을 메시지 큐에 등록한다.
3. 웹 서버는 이메일 발송 완료를 기다리지 않고 사용자에게 회원가입 결과를 반환한다.
4. 이메일 발송 서버가 메시지 큐에서 작업을 가져와 이메일을 발송한다.

**메시지 큐를 사용하는 이유**

- **비동기 처리:** 오래 걸리는 작업을 별도로 처리하여 사용자 응답시간을 줄일 수 있다.
- **서비스 분리:** 메시지를 보내는 시스템과 처리하는 시스템이 직접 연결될 필요가 없다.
- **트래픽 대응:** 요청이 급증하면 작업을 큐에 보관하고 소비자가 처리 가능한 속도로 처리한다.
- **장애 대응:** 소비자에 장애가 발생해도 메시지를 보관하고 이후 재처리할 수 있도록 설계할 수 있다.

**핵심:** 메시지 큐는 단순히 작업을 저장하는 공간이 아니라, 생산자와 소비자를 분리하여 비동기 처리와 시스템 간 의존성 감소를 가능하게 하는 구조다.

#### 주요 구성 요소

- **DNS:** 도메인 이름에 해당하는 IP 주소를 조회한다.
- **로드밸런서:** 사용자의 요청을 여러 웹 서버에 분산한다.
- **웹 서버:** 사용자 요청을 받아 필요한 작업을 처리한다.
- **캐시:** 자주 조회하는 데이터를 저장하여 응답속도를 개선한다.
- **데이터베이스:** 서비스에 필요한 데이터를 저장하고 관리한다.

#### 전체 요청 처리 흐름

1. 사용자가 Web/App을 통해 서비스에 접속한다.
2. DNS를 통해 도메인에 해당하는 IP 주소를 확인한다.
3. 사용자의 요청은 로드밸런서를 거쳐 여러 웹 서버에 분산된다.
4. 웹 서버는 요청에 필요한 데이터를 캐시 또는 데이터베이스에서 조회하거나 필요한 작업을 처리한다.
5. 처리 결과를 사용자에게 반환한다.

#### 직접 설명 및 그림 그리기 연습의 목적 알기
- DNS, 로드밸런서, 웹 서버, 캐시, DB의 역할을 설명할 수 있는가?
- 사용자 요청이 어떤 순서로 처리되는지 설명할 수 있는가?
- 로드밸런서를 사용하는 이유를 설명할 수 있는가?
- 캐시에 데이터가 있는 경우와 없는 경우의 차이를 설명할 수 있는가?
- 구성 요소를 직접 그린 뒤 요청 처리 흐름을 설명할 수 있는가?

**핵심:** 사용자의 요청이 DNS를 거쳐 서비스에 전달되고, 로드밸런서가 요청을 분산하며, 웹 서버가 캐시 또는 DB를 활용해 요청을 처리하는 전체 흐름을 이해하는 것이 중요하다.

### 6. QPS 계산 방식

**추가 질문 이유:** QPS의 개념과 계산 방식을 실제 서비스 예시를 통해 이해하기 위함.

#### 주요 개념

- **QPS:** 1초 동안 시스템에서 처리하는 요청 또는 질의의 수.
- **DAU:** 하루 동안 서비스를 이용하는 활성 사용자 수.
- **MAU:** 한 달 동안 서비스를 이용하는 활성 사용자 수.
- **평균 QPS:** 일정 기간의 전체 요청 수를 초 단위로 나눈 값.
- **최대 QPS:** 요청이 집중되는 시간대에 발생하는 초당 최대 요청 수.

#### QPS 계산 공식

평균 QPS = (DAU × 사용자당 하루 평균 요청 수) / 86,400초

※ 하루는 24시간 × 60분 × 60초 = 86,400초

#### 계산 예시 (쇼핑몰 서비스)

**가정**
- 일간 활성 사용자(DAU): 100만 명
- 사용자당 하루 평균 요청 수: 10회
- 최대 QPS: 평균 QPS의 2배로 가정

**계산 과정**

1. 하루 전체 요청 수
   - 1,000,000명 × 10회 = 10,000,000회

2. 평균 QPS
   - 10,000,000 / 86,400 ≈ 116

3. 최대 QPS
   - 116 × 2 ≈ 232

**계산 결과**
- 평균 QPS: 약 116
- 최대 QPS: 약 232

#### 평균 QPS와 최대 QPS의 차이

- **평균 QPS:** 하루 전체 요청을 86,400초로 나눈 평균값.
- **최대 QPS:** 특정 시간대에 요청이 집중되었을 때의 최대 처리량.
- 예를 들어 쇼핑몰 할인 행사나 특정 시간대에 사용자가 몰리면 평균 QPS보다 훨씬 높은 요청량이 발생할 수 있다.
- 최대 QPS를 평균의 2배로 계산하는 것은 예제의 가정이며, 실제 서비스의 트래픽 특성에 따라 달라진다.

**핵심:** QPS는 시스템이 초당 처리해야 하는 요청량을 추정하기 위한 지표다. 이를 통해 필요한 서버 처리 능력을 가늠할 수 있으며, 시스템 설계 시 평균 QPS뿐 아니라 최대 QPS도 함께 고려해야 한다.
