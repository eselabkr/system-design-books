## 어디서 막혔나

책(2021년 출간)의 개략적 설계 예시는 웹/모바일 클라이언트와 사람이 쓰는 서비스를 전제로 한다. 요즘은 AI로 코드를 빠르게 만들고(바이브 코딩), 에이전트가 사람 대신 서비스를 호출하며, 서비스 안에 LLM이 들어가기도 한다. 이런 변화가 책의 4단계 접근법과 핵심 컴포넌트에 무엇을 바꾸는지, 아니면 바꾸지 않는지 감이 오지 않았다. 이 주제는 책에 근거가 없어서 AI에게 물을 수밖에 없었고, 그만큼 답을 그대로 믿기 어렵다.

## 어떻게 물었나

1. 장 노트의 "더 알아볼 것"(AI로 인한 바이브 코딩, 에이전트가 시스템 설계에 어떤 영향을 미쳤는지)을 그대로 AI에게 던졌다.
2. 답이 뭉뚱그려질 수 있어서, 영향을 "클라이언트가 바뀌는 것 / 컴포넌트가 추가되는 것 / 설계하는 사람의 일이 바뀌는 것"으로 나눠서 정리해 달라고 요청했다.

## 무엇이 풀렸나

### 0. 한눈에 보기

| 층위 | 무슨 일이 일어났나 | 책의 어느 부분과 이어지나 |
| --- | --- | --- |
| ① 클라이언트 | 사람뿐 아니라 AI 에이전트·봇도 서비스를 호출한다 | 3장 핵심 컴포넌트의 "클라이언트", 4장 처리율 제한 |
| ② 컴포넌트 | LLM 추론이 서비스 안의 새 컴포넌트가 된다 | 2장 규모 추정, 1장 캐시·메시지 큐 |
| ③ 설계하는 사람 | 구현은 빨라지고, 요구사항 정의와 판단이 더 중요해진다 | 3장 4단계 접근법 |

### 1. 클라이언트가 바뀐다: 에이전트가 호출하는 서비스

- **트래픽 성격**: 사람은 클릭 사이에 시간이 있지만, 에이전트는 한 작업 안에서 API를 짧은 시간에 연속·병렬로 호출한다. 실패하면 자동으로 재시도하기도 한다. 그래서 평균 QPS는 같아도 **순간 최대 QPS가 더 날카롭게** 튈 수 있다(2장의 최대 QPS 가정을 다시 보게 된다).
- **처리율 제한**: 사용자 단위 외에 API 키·에이전트 단위로 제한을 건다. 요청 수 외에 비용이 큰 호출(예: LLM 호출)은 토큰·비용 기준으로 제한하기도 한다. 이어지는 4장(처리율 제한 장치)에서 다시 다룰 주제다.
- **멱등성**: 재시도가 잦으므로 같은 요청이 두 번 와도 결과가 한 번 처리한 것과 같아야 한다. 결제·주문 같은 쓰기 API에는 멱등 키(idempotency key)가 사실상 필수다.
- **기계가 읽기 쉬운 API**: 에이전트는 화면이 아니라 API 명세로 서비스를 이해한다. 명세(OpenAPI 등)가 정확해야 하고, 오류 응답이 사람이 읽는 문장이 아니라 코드와 구조화된 메시지여야 한다. 에이전트가 도구를 호출하는 표준 방식(MCP 등)에 맞춰 서비스를 노출하는 경우도 생겼다.
- **인증과 권한**: "사용자를 대신해 행동하는 에이전트"에게 어디까지 권한을 줄지(최소 권한, 범위 제한된 토큰, 감사 로그)가 새 설계 항목이 된다.

### 2. 컴포넌트가 늘어난다: LLM 추론을 품은 서비스

기존 구조에 LLM이 들어오면 이런 요소가 추가되거나 달라진다.

```text
 클라이언트 ─▶ LB ─▶ 웹 서버 (인증 · 처리율 제한[요청+토큰])
                         │
                         ▼
                   AI 게이트웨이/오케스트레이터 ──▶ 응답 캐시 (같은/비슷한 질문)
                         │          │
                         │          └──▶ 벡터 DB / 검색 (RAG: 관련 문서 찾기)
                         ▼
                   LLM 추론 서버 (GPU)  ──▶ 토큰을 스트리밍으로 응답
                         │
                         └──▶ 메시지 큐 ─▶ 긴 작업 워커 (배치 요약, 임베딩 생성 등)
```

| 요소 | 왜 필요한가 | 기존 개념과의 연결 |
| --- | --- | --- |
| LLM 추론 서버 (GPU) | 모델 실행에 GPU가 필요하고, 비싸고 수가 한정돼 있다 | 2장에서 정리한 GPU 병목(memory-bound, 대역폭)이 그대로 서버 수 추정에 쓰인다 |
| 스트리밍 응답 (SSE 등) | 응답이 수 초 이상 걸리므로 토큰을 만드는 대로 흘려보내 체감 지연을 줄인다 | 일반 요청-응답(수십~수백 ms)과 다른 응답 시간 가정 |
| 큐와 비동기 처리 | 오래 걸리는 작업은 응답 경로 밖에서 처리한다 | 1장·3장의 메시지 큐 |
| 응답 캐시 | 같거나 의미가 비슷한 질문의 결과를 재사용해 비용과 지연을 줄인다. 같은 질문이 정확히 반복되는 경우는 일반 캐시, 비슷한 질문은 임베딩을 이용한 캐시(시맨틱 캐시) | 1장의 캐시 |
| 벡터 DB / 검색 (RAG) | 모델이 모르는 내 데이터를 근거로 답하게 하려고 관련 문서를 먼저 찾아 붙인다 | 3장의 "데이터 저장소" 종류가 늘어남 |
| 모델 라우팅·폴백 | 질문 난이도에 따라 작은 모델/큰 모델을 고르고, 한 모델이 실패하면 다른 모델로 넘긴다 | 2장 가용성(장애 대비) |
| 비용·사용량 관측 | 요청당 비용이 매번 달라서 토큰 수, 지연, 실패율, 비용을 따로 추적해야 한다 | 일반 모니터링에 비용 지표가 추가됨 |

- **규모 추정이 달라지는 지점**: 요청 수(QPS)에 더해 **요청당 토큰 수**와 **초당 토큰 처리량**, 동시에 열려 있는 스트리밍 연결 수를 추정한다. 2장의 방식(가정 → 근사 계산 → 단위 표기)은 그대로 쓰이고, 숫자의 종류만 늘어난다.
- **결과가 항상 같지 않다**: 같은 입력에도 출력이 달라질 수 있어, 일반 서비스처럼 "맞다/틀리다"로 테스트하기 어렵다. 평가 데이터셋과 응답 품질 모니터링이 필요하다.
- **보안**: 프롬프트 인젝션(입력이나 검색된 문서에 숨은 명령이 모델을 조종), 모델이 호출하는 도구의 권한 과다, 민감 데이터가 프롬프트·로그로 새는 문제가 새로 생긴다.

### 3. 설계하는 사람의 일이 바뀐다: 바이브 코딩

- **구현 비용이 내려간다**: 동작하는 코드를 만드는 속도가 빨라져서, 병목이 "코드를 쓰는 일"에서 **"무엇을 만들지 정하고 맞는지 판단하는 일"**로 옮겨 간다.
- **3장이 오히려 더 중요해진다**: 요구사항을 명확히 하고, 가정을 세우고, 트레이드오프를 설명하는 능력(3장 4단계 접근법의 1~2단계)은 AI가 대신해 주기 어렵다. AI에게 시킬 때도 이 정보를 정확히 줘야 쓸 만한 결과가 나온다.
- **검증 책임은 사람에게**: AI가 만든 코드는 그럴듯하지만 보안 취약점, 숨은 가정(트래픽 규모, 동시성), 일관성 없는 구조를 가질 수 있다. 설계안을 평가하는 기준(병목, 장애 지점, 비용)을 사람이 알고 있어야 걸러낼 수 있다.
- **면접에 주는 시사점**: 인상 깊은 구절(p.40)의 평가 요소 — 좋은 질문, 모호한 문제 정의, 협력 — 이 AI 시대에 더 무게를 받는다고 볼 수 있다. 다만 이건 내 해석이고, 면접 방식이 실제로 어떻게 바뀌는지는 확인한 바 없다.

### 4. 내가 이해하게 된 것

- AI가 시스템 설계의 **원칙**을 바꾼 것은 아니다. 캐시, 큐, 처리율 제한, 규모 추정 같은 기본기는 그대로 쓰이고, 새 컴포넌트(LLM 추론, 벡터 DB)와 새 클라이언트(에이전트)가 **같은 도구 상자에 추가**됐다.
- 오히려 기본기가 약하면 AI가 만든 설계의 문제를 알아보지 못한다. 2장의 지연·규모 감각과 3장의 질문하는 습관이 AI 시대에도 밑바탕이다.
- "AI가 설계를 어떻게 바꿨나"는 변화가 빨라서 이 문서의 내용도 금방 낡을 수 있다. 시점(2026-10)을 기준으로 읽어야 한다.
