## 어디서 막혔나

3장은 개략적인 설계안에 "클라이언트, API, 웹 서버, 데이터 저장소, 캐시, CDN, 메시지 큐"를 넣으라고 이름만 나열한다. 각 컴포넌트가 정확히 무엇을 맡는지, 요청 하나가 이들을 어떤 순서로 지나가는지는 뉴스 피드 그림(그림 3-3, 3-4)에서 눈으로 따라가야 했다. 그림의 박스는 보이는데, 왜 그 자리에 있고 화살표가 왜 그 방향인지 설명이 없어 이해가 덜 됐다. API 엔드포인트와 데이터베이스 스키마가 무엇을 가리키는지도 흐릿했다.

## 어떻게 물었나

1. 장 노트의 "더 알아볼 것" 첫 항목(각 컴포넌트의 세부 기능 및 동작 순서)을 그대로 AI에게 던졌다.
2. 개념 설명만으로는 부족해, 책의 그림 3-3(피드 발행)과 3-4(피드 가져오기)를 기준으로 요청이 지나가는 순서를 단계별로 풀어 달라고 요청했다.

## 무엇이 풀렸나

### 0. 큰 그림

```text
                         ┌──────────── CDN (이미지·동영상·JS·CSS) ◀── 클라이언트가 미디어를 직접 받음
                         │
 클라이언트 ──▶ DNS ─────┘ (도메인 → IP)
 (웹/모바일)
     │ API 요청
     ▼
 로드 밸런서 ──▶ 웹 서버 (인증 · 처리율 제한) ──▶ 서비스 로직
                                                   │
                         ┌─────────────────────────┼──────────────────────┐
                         ▼                         ▼                      ▼
                       캐시 ──(miss)──▶ 데이터 저장소(DB)           메시지 큐 ──▶ 워커
                      (빠른 읽기)        (원본, 영속)               (비동기 후처리)
```

핵심은 **"빠르게 답할 것은 앞쪽(CDN·캐시)에서 끝내고, 느리거나 무거운 것은 뒤쪽(큐·워커)으로 미룬다"**는 역할 분담이다. 2장의 지연 값 표(메모리 ≪ 디스크, 데이터 센터 간 통신은 느림)가 이 구조의 이유다.

### 1. 컴포넌트별 기능

| 컴포넌트 | 하는 일 | 이 장 뉴스 피드에서는 |
| --- | --- | --- |
| 클라이언트 (웹 브라우저, 모바일 앱) | 화면을 그리고 API를 호출한다. 인증 토큰을 들고 다니며, 로컬 캐시를 가질 수도 있다 | 포스팅 요청과 피드 요청을 보내는 쪽 |
| DNS | 도메인 이름을 IP 주소로 바꿔 준다 | 그림에서 단말 옆에 붙어 있는 DNS 아이콘 |
| CDN | 사용자와 가까운 엣지 서버에 정적 파일을 캐시해 둔다. 엣지에 있으면(hit) 바로 주고, 없으면(miss) 원본 서버에서 받아 와 저장한 뒤 준다 | 그림 3-4에서 단말이 이미지·동영상을 CDN에서 직접 받음 |
| 로드 밸런서 | 들어오는 요청을 여러 웹 서버에 나눠 준다. 헬스 체크로 죽은 서버를 빼고, 서버를 늘려도 클라이언트는 모른다 | 단말 바로 다음 단계 |
| 웹 서버 | 요청을 받아 공통 처리(인증, 처리율 제한 등)를 하고 뒤의 서비스로 넘긴다 | 그림의 점선 박스 안 "인증", "처리율 제한" |
| API | 클라이언트와 서버 사이의 약속이다. 엔드포인트(URL), 메서드, 요청·응답 형식, 인증 방식을 정한다 | 포스팅: `v1/me/feed?content=Hello&auth_token=...` / 피드 조회: `/v1/me/feed` |
| 서비스 (포스팅 저장, 포스팅 전송, 뉴스 피드, 알림) | 비즈니스 로직을 맡는다. 웹 서버 뒤에서 역할별로 나뉜다 | 그림의 둥근 박스들 |
| 캐시 | 자주 읽는 데이터를 메모리에 둬서 DB 접근을 줄인다 | 포스팅 캐시, 사용자 정보 캐시, 뉴스 피드 캐시 |
| 데이터 저장소 | 원본 데이터를 영속적으로 보관한다. 데이터 성격에 따라 종류를 나눈다 | 포스팅 DB, 사용자 정보 DB, 그래프 DB(친구 관계) |
| 메시지 큐 | 보내는 쪽(producer)이 메시지를 넣고 받는 쪽(consumer)이 꺼내 처리한다. 둘이 서로를 기다리지 않는다 | 포스팅 전송 서비스와 전송 작업 서버 사이 |
| 데이터베이스 스키마 | 테이블, 컬럼, 키, 인덱스 같은 데이터의 구조 정의 | 그림에는 없지만 개략적 설계에 함께 제시하라는 항목 |

세부 메모:

- **웹 서버와 API 서버**: 책은 "웹 서버"로 묶어 그리지만, 실무에서는 Nginx 같은 프록시(TLS 종료, 정적 파일, 라우팅)와 비즈니스 로직을 도는 애플리케이션 서버로 나눠 두는 경우가 많다.
- **캐시 읽기 패턴**: 대표적으로 읽을 때 캐시를 먼저 보고, 없으면 DB에서 읽어 캐시에 채운 뒤 돌려준다(cache-aside). 값이 바뀌면 캐시를 지우거나 갱신해 DB와 어긋나지 않게 한다.
- **메시지 큐를 쓰는 이유**: ① 처리가 느린 일을 응답 경로 밖으로 뺀다 ② 쓰는 쪽과 받는 쪽의 속도 차이를 완충한다(트래픽이 몰려도 큐에 쌓아 두고 순서대로 처리) ③ 받는 쪽이 잠시 죽어도 메시지가 큐에 남아 있다가 재처리된다.
- **데이터 저장소 선택**: 관계가 복잡하고 일관성이 중요하면 관계형 DB, 데이터가 아주 많고 수평 확장이 중요하면 NoSQL, 친구 관계처럼 "연결"이 핵심이면 그래프 DB를 쓴다(1장의 NoSQL 내용과 이어짐).

### 2. 동작 순서 ① 피드 발행 (그림 3-3: 쓰기 경로)

1. 사용자가 새 글을 올린다. 클라이언트가 포스팅 API(`v1/me/feed`)를 호출한다. 내용(content)과 인증 토큰(auth_token)이 함께 간다.
2. 요청이 로드 밸런서를 거쳐 웹 서버 한 대로 간다.
3. 웹 서버가 **인증**(올바른 사용자인가)과 **처리율 제한**(너무 자주 올리지 않는가)을 확인한다. 통과하면 서비스로 넘긴다.
4. **포스팅 저장 서비스**가 글을 포스팅 DB에 저장하고 포스팅 캐시에도 둔다. **알림 서비스**는 별도로 알림을 보낸다.
5. **포스팅 전송 서비스**가 이 글을 친구들의 피드에 퍼뜨리는 일(팬아웃)을 맡는다.
   - ① 그래프 DB에서 **친구 id 목록**을 가져온다.
   - ② 사용자 정보 캐시(없으면 DB)에서 **친구 데이터**를 가져온다. 설정에 따라 일부 친구는 제외할 수도 있다.
   - ③ 친구 목록과 새 글 id를 **메시지 큐**에 넣는다.
6. ④ **포스팅 전송 작업 서버**(워커)가 큐에서 메시지를 꺼내 처리한다.
7. ⑤ 각 친구의 **뉴스 피드 캐시**에 `<글 id, 사용자 id>` 쌍을 추가한다. 글 전체를 복사하지 않고 id만 저장해 메모리를 아낀다.

→ 사용자의 요청은 4번에서 저장이 끝나면 응답할 수 있고, 친구 수만큼 퍼뜨리는 무거운 일은 큐 뒤에서 비동기로 처리한다. 이것이 메시지 큐가 여기 있는 이유다.

### 3. 동작 순서 ② 피드 가져오기 (그림 3-4: 읽기 경로)

1. 사용자가 피드 화면을 열면 클라이언트가 `/v1/me/feed`를 호출한다.
2. 로드 밸런서가 웹 서버로 보내고, 웹 서버가 인증과 처리율 제한을 확인한다.
3. 웹 서버가 **뉴스 피드 서비스**를 호출한다.
4. 뉴스 피드 서비스가 **뉴스 피드 캐시**에서 이 사용자의 피드 `<글 id, 사용자 id>` 목록을 꺼낸다.
5. id만으로는 화면을 못 그리므로, **사용자 정보 캐시**와 **포스팅 캐시**(없으면 각 DB)에서 사용자 이름, 프로필 사진, 글 내용 등을 가져와 채운다.
6. 완성된 피드를 JSON 형태로 클라이언트에 돌려준다.
7. 피드에 들어 있는 이미지·동영상은 클라이언트가 **CDN**에서 직접 받는다. 웹 서버를 거치지 않는다.

→ 읽기는 거의 전부 캐시에서 끝난다. 피드를 **미리 만들어 캐시에 넣어 두는** 발행 경로의 작업이 있기 때문에 가능하다. 쓰기에서 일을 많이 해 두고 읽기를 가볍게 만든 구조다.

### 4. 내가 이해하게 된 것

- 컴포넌트 이름을 외우는 것보다 **"이 박스가 없으면 어떤 문제가 생기나"**로 보면 이유가 보인다. 로드 밸런서가 없으면 서버 한 대에 몰리고, 캐시가 없으면 DB가 읽기를 다 받고, 큐가 없으면 글 하나 올릴 때마다 친구 수만큼 기다려야 하고, CDN이 없으면 이미지가 먼 서버에서 온다.
- 읽기 경로와 쓰기 경로를 나눠서 그리면 그림이 훨씬 읽기 쉬워진다. 면접에서도 두 흐름으로 나눠 설명하는 편이 좋겠다.
- 그림에서 "누가 누구를 부르는가"가 중요하다. 단말이 CDN을 직접 부르는 점, 웹 서버가 모든 걸 중계하지 않는 점이 눈에 들어왔다.
