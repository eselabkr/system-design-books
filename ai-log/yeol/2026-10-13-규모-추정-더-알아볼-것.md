## 무엇이 풀렸나

### 1. 메모리는 빠르지만 디스크는 왜 느린가

- **물리적 차이**: 메모리(DRAM)는 전기 신호로 주소를 찾아 읽는다. 하드디스크(HDD)는 회전하는 원판 위로 헤드를 기계적으로 움직여야 한다. 전기 신호는 나노초 단위, 기계 움직임은 밀리초 단위다.
- **자릿수 차이**: 책 표 기준 메모리 참조 약 100ns, 디스크 탐색 약 10ms. 10ms / 100ns = 10^5, 즉 약 10만 배다.
- **SSD는 어떤가**: SSD는 기계 부품이 없어 HDD보다 훨씬 빠르다. 그래도 메모리보다는 보통 수백~천 배 느리다. 메모리는 CPU와 가까운 메모리 버스에 직접 붙어 있고, SSD는 컨트롤러와 I/O 인터페이스를 거치기 때문이다.
- **휘발성과 용량 맞교환**: 메모리는 전원이 꺼지면 사라지고 GB당 비싸다. 디스크는 영속적이고 싸서 큰 용량을 담는다. 그래서 자주 쓰는 것은 메모리에, 나머지는 디스크에 두는 계층 구조를 쓴다.

### 2. "디스크 탐색(seek)"은 CPU가 하드디스크로 넘어가는 것인가

내 이해는 반만 맞았다.

- **seek의 좁은 의미**: HDD에서 읽을 데이터가 있는 트랙 위치로 **디스크 헤드를 물리적으로 옮기는 동작**이다. CPU가 어디로 "넘어가는" 것이 아니다.
- **전체 흐름**: 프로그램이 파일을 읽으면 → 운영체제가 요청을 디스크 드라이버로 보내고 → 디스크가 헤드를 옮기고(seek) 원판이 돌아 원하는 섹터가 올 때까지 기다린(회전 지연) 뒤 → 데이터를 읽어 메모리로 복사(보통 DMA)하면 → CPU가 이어서 쓴다. 그동안 CPU는 대개 다른 일을 하거나 기다린다.
- **책에서의 의미**: 넓게는 "디스크에서 임의 위치의 데이터를 읽는 I/O 한 번"을 뜻하는 말로 쓴다.

### 3. 디스크 탐색은 왜 가장 비싼 연산인가

- **seek 시간 + 회전 지연**이 겹친다. 7,200rpm 디스크는 반 바퀴 도는 데만 평균 약 4ms가 걸린다. 여기에 헤드 이동 시간이 더해진다.
- **한 번 시작하면 비용이 고정**이다. 읽는 양이 1바이트든 4KB든 위치를 찾는 비용은 똑같다.
- **임의 접근 vs 순차 접근**: 순차로 쭉 읽으면 한 번 찾은 뒤 계속 읽으므로 처리량이 좋다. 여기저기 흩어진 데이터를 읽으면 매번 탐색 비용을 내서 극단적으로 느려진다.
- **설계로 이어지는 방식**: 임의 읽기를 줄이려고 캐시를 두고, 쓰기를 순차 로그로 모으고(LSM 트리, 쓰기 선행 로그), 인덱스로 읽을 위치를 줄인다.

### 4. CPU에서 GPU로 넘어가는 과정과 병목

> 이 절의 수치는 GPU 세대와 모델마다 다르다. 자릿수와 비율을 보기 위한 대략값이다.

#### 4-1. 왜 GPU로 넘기는가

| | CPU | GPU |
| --- | --- | --- |
| 코어 | 수 개~수십 개의 강력한 코어 | 수천 개의 단순한 코어 |
| 잘하는 일 | 복잡한 분기, 순차 로직, 낮은 지연 | 같은 연산을 많은 데이터에 동시에 적용(SIMT), 높은 처리량 |
| 설계 목표 | 한 작업을 빨리 끝내기 (latency) | 많은 작업을 한꺼번에 끝내기 (throughput) |

행렬 곱은 결과 행렬의 원소 하나하나를 서로 독립적으로 계산할 수 있어 GPU에 잘 맞는다. 그래서 딥러닝의 텐서·행렬 연산을 GPU로 보낸다.

#### 4-2. 하드웨어 구조와 계층별 속도

```text
 디스크/SSD ──▶ CPU + RAM(DDR) ══ PCIe ══▶ GPU + VRAM(HBM/GDDR)
   (수 GB/s)     (수십~백 GB/s)  (수십 GB/s)     (수백 GB/s ~ 수 TB/s)
```

| 구간 | 대략적인 대역폭 | 메모 |
| --- | --- | --- |
| NVMe SSD → RAM | 약 3~7 GB/s | PCIe 4.0 x4 기준 |
| CPU ↔ RAM (DDR5) | 약 50~100 GB/s (서버는 더 큼) | 채널 수에 따라 다름 |
| CPU ↔ GPU (PCIe 4.0 x16) | 약 32 GB/s (단방향 이론치) | PCIe 5.0 x16은 약 64 GB/s |
| GPU ↔ GPU (NVLink) | 수백 GB/s (H100급은 900 GB/s 수준) | PCIe보다 한 자릿수 빠름 |
| GPU 코어 ↔ VRAM (HBM) | 약 2~3.5 TB/s (A100~H100급) | 소비자용 GDDR GPU는 수백 GB/s~1 TB/s대 |

핵심은 **GPU 내부 메모리(VRAM) 대역폭이 CPU↔GPU를 잇는 PCIe 대역폭보다 수십~백 배 크다**는 점이다. 그래서 데이터를 GPU로 한 번 올려 두고 그 안에서 최대한 계산하는 것이 기본 전략이다. 2장의 "메모리는 빠르지만 디스크는 느리다"와 같은 계층 구조 논리다.

GPU 내부에도 계층이 있다: 레지스터 → 공유 메모리/L1 → L2 캐시 → VRAM(HBM). 가까울수록 빠르고 작다. GPU는 32개 스레드 묶음(warp) 단위로 같은 명령을 실행한다.

#### 4-3. 학습 한 스텝에서 일어나는 일 (PyTorch 기준)

```python
model = model.to("cuda")                       # ① 가중치를 GPU에 상주시킴 (최초 1회 복사)
for x, y in loader:                            # ② CPU: 디스크 읽기 + 디코딩 + 증강 (DataLoader 워커 프로세스)
    x = x.to("cuda", non_blocking=True)        # ③ CPU RAM → GPU VRAM 복사 (PCIe, DMA)
    y = y.to("cuda", non_blocking=True)
    loss = loss_fn(model(x), y)                # ④ forward: 연산마다 GPU 커널 실행 요청
    loss.backward()                            # ⑤ backward: 기울기 계산 (GPU 안에서)
    optimizer.step()                           # ⑥ 가중치 갱신 (GPU 안에서)
    optimizer.zero_grad()
    print(loss.item())                         # ⑦ GPU → CPU로 값 가져옴 (동기화 발생)
```

단계별로 풀면 이렇다.

1. **데이터 준비 (CPU)**: DataLoader 워커가 스토리지에서 읽어 이미지 디코딩, 크기 조정, 증강을 한다. CPU 코어와 스토리지 속도가 여기서 결정된다.
2. **호스트 → 디바이스 복사**: 배치를 GPU 메모리로 복사한다. 보통 메모리는 OS가 디스크로 내보낼 수 있는(pageable) 상태라서, 먼저 임시 고정(pinned) 버퍼로 한 번 더 복사한 뒤 보낸다. `pin_memory=True`로 처음부터 고정(page-locked) 메모리를 쓰면 이 복사가 줄고, `non_blocking=True`로 CPU가 복사 완료를 기다리지 않고 다음 일을 할 수 있다.
3. **커널 실행 요청**: 파이썬 코드가 연산 하나(행렬 곱, 덧셈, 활성화 등)를 만날 때마다 CPU가 GPU에 "이 커널을 실행해" 라는 요청을 **스트림 큐에 넣고 바로 돌아온다**. GPU는 큐에서 하나씩 꺼내 실행한다. 이 비동기 구조 덕분에 CPU가 GPU보다 앞서 달리며 요청을 쌓아 둘 수 있다.
4. **GPU 계산**: SM(Streaming Multiprocessor) 여러 개가 병렬로 일한다. 행렬 곱은 Tensor Core 같은 전용 유닛을 쓴다.
5. **결과 회수와 동기화**: `loss.item()`, `.cpu()`, `print(tensor)`처럼 GPU 값을 CPU가 읽는 순간, CPU는 큐에 쌓인 GPU 작업이 모두 끝날 때까지 기다린다(동기화). 이때 비동기의 이점이 사라진다.

#### 4-4. 병목이 생기는 곳과 확인 방법

| 병목 지점 | 증상 | 확인 방법 | 대응 |
| --- | --- | --- | --- |
| 스토리지 읽기 | GPU 사용률이 주기적으로 0에 가까워진다 | `iostat`, 데이터 로더 시간 측정 | NVMe SSD, 데이터를 큰 파일로 묶기(샤딩), 캐시 |
| CPU 전처리 | 워커 CPU가 100%인데 GPU는 논다 | `top`, PyTorch Profiler의 DataLoader 구간 | `num_workers` 늘리기, `prefetch_factor`, `persistent_workers`, 전처리를 GPU로 이동 |
| CPU → GPU 전송 | 복사 시간이 연산보다 길다 | Profiler의 `Memcpy HtoD` | `pin_memory=True`, 복사 횟수·크기 줄이기, 데이터를 GPU에 상주시키기 |
| 커널 실행 오버헤드 | 작은 연산이 아주 많아 GPU가 틈틈이 논다 (CPU가 launch를 못 따라감) | Nsight Systems 타임라인의 빈틈 | 연산 융합(`torch.compile`), CUDA Graphs, 배치 키우기 |
| 잦은 동기화 | CPU와 GPU가 번갈아 기다린다 | 타임라인에서 sync 지점 | `.item()`·`.cpu()` 호출 줄이기, 로그는 몇 스텝에 한 번만 |
| GPU 메모리 대역폭 | 연산 유닛은 놀고 메모리만 바쁘다 (memory-bound) | Nsight Compute, roofline | FP16/BF16, 연산 융합, 메모리 접근 줄이기 |
| GPU 연산량 | 연산 유닛이 가득 찼다 (compute-bound) | 위와 같음 | Tensor Core 활용(혼합 정밀도), 더 빠른 GPU |
| GPU 메모리 부족 | OOM(Out Of Memory) | `nvidia-smi` | 배치 줄이기, gradient accumulation, gradient checkpointing |
| 다중 GPU 통신 | 분산 학습에서 GPU 수를 늘려도 속도가 안 오른다 | 타임라인의 all-reduce 구간 | NVLink·InfiniBand, 통신과 연산 겹치기, 기울기 압축 |

참고: `nvidia-smi`의 GPU-Util은 "측정 구간 중 커널이 하나라도 실행 중이던 시간 비율"이다. 높다고 해서 GPU 코어를 꽉 채워 쓴다는 뜻은 아니다. 정확한 진단에는 PyTorch Profiler나 Nsight Systems를 쓴다.

#### 4-5. memory-bound vs compute-bound

- **연산 강도(arithmetic intensity)** = 연산 횟수(FLOPs) ÷ 메모리에서 옮긴 바이트 수.
- **Roofline 모델**: 달성 가능한 성능 ≈ min(피크 연산 성능, 메모리 대역폭 × 연산 강도). 연산 강도가 낮으면 메모리 대역폭이, 높으면 연산 성능이 한계가 된다.

| 연산 | 연산 강도 | 한계 | 설명 |
| --- | --- | --- | --- |
| 큰 행렬 곱 (N×N) | 높음 (N에 비례) | compute-bound | 연산은 약 2N³, 옮기는 데이터는 약 3N²에 비례해서 N이 클수록 읽은 데이터를 많이 재사용한다 |
| 원소별 연산 (덧셈, ReLU) | 매우 낮음 (FP32 기준 약 0.1 FLOP/byte) | memory-bound | 값 하나를 읽고(4B) 쓰는(4B) 동안 연산은 한 번뿐이다 |
| LLM 추론의 토큰 생성 (배치 1) | 낮음 | memory-bound | 토큰 하나 만들 때마다 모든 가중치를 VRAM에서 읽어야 한다 |

LLM 추론으로 직접 추정해 보면 다음과 같다. 70억 파라미터 모델을 FP16으로 두면 가중치가 약 14GB다. 대역폭이 약 2TB/s인 GPU라면 토큰 하나당 가중치를 한 번 읽는 데 최소 14GB ÷ 2,000GB/s = 7ms가 든다. 따라서 배치 1에서 이론 상한은 초당 약 140 토큰이다. 이건 연산이 아니라 **메모리 읽기 속도**가 정한 한계다. 배치를 키우면 같은 가중치 읽기를 여러 요청이 나눠 쓰므로 연산 강도가 올라간다.

#### 4-6. 병목을 줄이는 대표 기법

- **데이터를 GPU에 오래 두기**: 가중치·중간 결과를 CPU로 왔다 갔다 하지 않는다.
- **전송과 연산 겹치기**: 다음 배치를 복사하는 동안 현재 배치를 계산한다(프리페치, 다중 스트림).
- **혼합 정밀도(FP16/BF16)**: 메모리 사용량과 이동량을 절반으로 줄이고 Tensor Core를 쓸 수 있다.
- **연산 융합**: 작은 연산 여럿을 한 커널로 묶어 VRAM 왕복과 launch 횟수를 줄인다(`torch.compile`, FlashAttention이 대표적).
- **배치 크기 조절**: 크게 하면 GPU 활용도가 오르지만 메모리를 더 쓴다.
- **분산 학습**: 데이터 병렬(DDP)은 각 GPU가 모델 전체를 갖고 기울기를 all-reduce로 합친다. 모델이 한 GPU에 안 들어가면 텐서/파이프라인 병렬을 쓴다. GPU 간 연결(NVLink, 노드 간 InfiniBand)이 성능을 좌우한다.

#### 4-7. 참고: CPU와 GPU가 메모리를 공유하는 경우

내 Mac처럼 Apple Silicon은 **통합 메모리(unified memory)** 구조라서 CPU와 GPU가 같은 물리 메모리를 쓴다. PCIe를 통한 복사 단계 자체가 없고, 대신 메모리 대역폭(칩 등급별로 수십~수백 GB/s)을 CPU와 GPU가 나눠 쓴다. PyTorch에서는 `"mps"` 장치로 쓰며, NVIDIA 전용 도구(`nvidia-smi`, Nsight)는 쓸 수 없다.

#### 4-8. 2장 방식으로 병목 추정해 보기

학습 입력이 이미지 1장당 150KB이고 GPU가 초당 2,000장을 처리한다고 가정하면 필요한 읽기 속도는 2,000 × 150KB = 300MB/s다.

- NVMe SSD(수 GB/s): 여유 있다.
- HDD: 순차 읽기는 약 100~200MB/s 수준이라 부족하고, 이미지 파일 여러 개를 임의 위치에서 읽으면 디스크 탐색이 끼어 훨씬 더 느려진다.

즉 "GPU가 빠른데 학습이 느리다"의 원인이 연산이 아니라 **스토리지 탐색 지연**일 수 있다. 앞선 2, 3절의 디스크 탐색 이야기와 이어지는 지점이다.

### 5. 단순한 압축 알고리즘의 예시

- **빠른 쪽**: LZ4, Snappy, LZO. 압축률은 낮지만 압축·해제가 매우 빠르다. Kafka, 데이터베이스 저장 엔진, 로그 전송에서 자주 쓴다.
- **균형**: Zstandard(zstd)는 레벨을 낮추면 빠르고, 높이면 압축률이 좋다.
- **압축률 중심**: gzip(deflate), brotli. 웹 응답에서 많이 쓴다. CPU를 더 쓴다.
- **기본 원리**: 반복 문자열을 앞에서 이미 나온 위치로 대체(LZ77 계열), 자주 나오는 값에 짧은 코드를 할당(허프만), 같은 값의 연속을 "값×횟수"로 표현(런렝스).
- **왜 전송 전에 압축하는가**: 압축·해제에 쓰는 CPU 시간보다, 줄어든 바이트를 네트워크로 보내는 시간 절약이 더 크기 때문이다. 이미 압축된 이미지·영상 등은 효과가 작다.

### 6. 업계에서 고가용성을 달성하는 주요 방법

- **단일 장애점(SPOF) 제거**: 모든 계층을 다중화한다. 서버, DB, 캐시, 로드밸런서 모두.
- **로드밸런서 + 헬스 체크**: 죽은 서버를 자동으로 빼고 살아 있는 서버로 트래픽을 보낸다.
- **데이터 복제와 자동 장애 조치(failover)**: 주 DB가 죽으면 복제본이 승격한다. 1장의 master-slave와 이어진다.
- **여러 가용 영역·리전에 분산**: 한 데이터 센터가 통째로 죽어도 서비스가 이어진다.
- **무상태 웹 계층 + 오토스케일링**: 서버를 쉽게 늘리고 교체한다.
- **장애 전파 차단**: 타임아웃, 재시도, 서킷 브레이커, 벌크헤드, 속도 제한, 우아한 성능 저하(graceful degradation).
- **안전한 배포**: 카나리, 블루/그린, 롤링 배포로 배포 때문에 생기는 장애를 줄인다.
- **관측과 대응**: 모니터링, 알림, 장애 대응 훈련(chaos engineering), 백업과 복구 목표(RTO/RPO)를 정한다.
- **목표 표현**: SLA/SLO와 가용성 수치(99.9% ≈ 연 8.8시간, 99.99% ≈ 연 53분, 99.999% ≈ 연 5분 다운타임).

### 7. QPS의 의미와 다른 서비스 예시

- **QPS**: 초당 서버가 처리해야 하는 쿼리(요청) 수. 평균과 **최대(peak)**를 구분한다. 읽기/쓰기 QPS를 따로 보기도 한다.
- **계산 틀**: DAU × 사용자당 하루 요청 수 ÷ 86,400 = 평균 QPS. 최대는 평균 × 2 정도로 가정한다(서비스마다 다름).
- **책 예시(트위터)**: DAU 1.5억 × 하루 2건 ÷ 86,400 ≈ 3,500, 최대 ≈ 7,000.

**다른 서비스로 직접 계산해 본 예 (가정은 모두 임의)**

| 서비스 | 가정 | 평균 QPS | 메모 |
| --- | --- | --- | --- |
| 쇼핑몰 API | DAU 100만, 1인당 하루 50회 호출 | 약 580 | 세일·이벤트 때 최대는 평균의 수 배~10배 이상 |
| 메신저 | DAU 1억, 1인당 하루 40건 전송 | 약 46,000 | 최대 약 9만. 수신 쪽 팬아웃까지 보면 더 커진다 |
| 티켓팅 | 평소 낮음, 오픈 순간 수십만 명이 몰림 | 평소 ≪ 최대 | 평균보다 최대 QPS 설계가 핵심. 대기열로 완화 |

- **QPS로 서버 수 가늠**: 동시 처리 수 ≈ QPS × 평균 응답 시간. 요청당 100ms, 서버가 동시에 200건을 처리하면 서버 1대 ≈ 2,000 QPS(이론치). 실제로는 여유를 둔다.
- **QPS 비슷한 용어**: RPS(초당 요청), TPS(초당 트랜잭션). 문맥에 따라 같은 뜻으로 쓰기도 한다.
