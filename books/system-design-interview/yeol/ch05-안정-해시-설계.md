## 핵심 내용

### Why we need Hash-key ?
: 수평적 규모 확장성을 달성하기 위해 서버풀에 데이터/요청을 고르게 분산해야 한다.

### 해시 키 재배치(rehash) 문제
* **전통적 해시**: `serverIndex = hash(key) % N`
  - 서버 수 N이 고정일 때 → 균등 분포 가능
  - 서버 추가/장애로 N이 바뀔 때 → 캐시 미스 상태 폭증 현상 발생할 수 있음 
* **문제 상황**: (서버 4대 중 1대 장애 시 키가 어떻게 재배치되는가? 캐시 미스 폭증) / (슬롯의 수가 바뀌면 거의 대부분 키를 재배치해야함)

### 안정 해시 (Consistent Hashing)
: 정의: 해시 테이블 크기가 조정될 때 평균적으로 오직 k/n개의 키만 재배치하는 기술. (k=키 개수, n=슬롯 개수)
- 안정 해시 알고리즘
   * 서버와 키를 균등 분포 해시 함수를 사용해 해시 링에 배치된
   * 키의 위치에서 링을 시계 방향으로 탐색하다 만나는 최초의 서버가 키가 저장될 서버 

### 해시 함수 (Hash Function) 
: 임의의 길이를 가진 입력 데이터(Key)를 고정된 길이의 고유한 숫자 값(해시 값)으로 변환하는 수학적 함수

### 해시 공간 (Hash Space) 
: 해시 함수가 출력할 수 있는 **모든 해시 값의 범위(집합)**

### 해시 링 (Hash Ring)
: 선형적인 해시 공간의 양 끝(0과 최댓값 2ⁿ - 1)을 이어 붙여 원형(고리 모양)으로 만든 구조

#### 해시 서버 / 해시 키 배치
* 서버를 `해시 링`에 배치
* `해시 키`를 링에 배치 (`나머지 연산 %`은 사용하고 있지 않음)

#### 서버 조회
* 규칙: 키 위치에서 `시계 방향`으로 가장 처음 만나는 서버

#### 서버 추가 / 제거
* **서버 추가** 시 재배치되는 키: 서버를 추가하더라도 키 가운데 일부만 재배치하면 된다. (연결리스트랑 비슷?)
* **서버 제거** 시 재배치되는 키: 하나의 서버가 제거되면 가운데 일부만 재배치된다. (연결리스랑 비슷?)

### 기본 구현의 두 가지 문제
1. **파티션 크기를 균등하게 유지하기 어렵다**
   - 파티션: 인접한 서버 사이 해시 공간 (서버에 따라 매우 작은 또는 큰 해시 공간을 할당 받는 상황 존재)

2. **키의 균등 분포를 달성하기 어렵다**
   - 특정 서버에 키가 몰리는 경우: 큰 파티션을 담당하던 서버가 과부하(메모리 부족, CPU 포화 등)를 견디지 못하고 다운되면,, 작은 서버로 트래픽이 몰릴거고, 연쇄 다운 발생 가능성 높아짐

-> 이 문제들을 해결하기 위해 가상 노드 또는 복제 기법이 사용됨 

### 가상 노드 (Virtual Node / Replica)
* 개념: 실제 서버(노드) 하나를 링 위의 여러 가상 노드로 표현
* 동작 방식:
```
s0_0, s0_1, s0_2 / s1_0, s1_1, s1_2 가 링에 섞여 배치된 그림
```
* 효과: 가상 노드 수 ↑ → 키 분포 표준 편차 ↓
* 트레이드오프: 가상 노드 수 ↑ → 메타데이터 저장 공간 ↑ (조정 필요)

### 재배치할 키 찾기
* 서버 추가 시: 새 서버 위치에서 **반시계 방향**으로 이웃 서버를 만날 때까지의 키 범위 →
* 서버 제거 시: 제거된 서버 위치에서 반시계 방향으로 이웃 서버를 만날 때까지의 키 범위 →

### 실제 안정 해시 사용 사례
- Amazon DynamoDB 파티셔닝
- Apache Cassandra 데이터 파티셔닝
- Discord 채팅 애플리케이션
- Akamai CDN
- Maglev 네트워크 부하 분산기

### 정리
* 안정해시 장점 :
  - 서버 추가/삭제 시 재배치되는 키가 최소화된다
  - 데이터가 보다 균등하게 분포 → 수평적 규모 확장성 달성, 핫스팟 키 문제 감소
  - 핫스팟 키 문제 감소 : 특정한 샤드(shard)에 접근이 지나치게 빈번하여 서버 과부하 문제를 일으킬 수 있는데 데이터를 균등하게 분포하여 문제 가능성 낮춤 
  - 수평적 확장에 유리

## 면접 예상 질문

1. **Q. 나머지 연산(`hash(key) % N`) 방식으로 서버를 고르면 어떤 문제가 생기는가?**

   **A.** 서버 수 N이 고정일 때는 키가 고르게 분산되지만, 서버가 추가되거나 장애로 빠져 N이 바뀌면 거의 모든 키의 `hash(key) % N` 결과가 달라진다. 그래서 대부분의 키가 다른 서버로 재매핑되고, 캐시라면 한꺼번에 캐시 미스가 발생해 원본 DB로 요청이 몰린다. 장애가 난 서버 쪽 키만 옮기면 되는데도 전체가 흔들리는 것이 문제다.

2. **Q. 안정 해시란 무엇이고, 어떻게 재배치 문제를 줄이는가?**

   **A.** 해시 테이블 크기(서버 수)가 바뀔 때 평균적으로 k/n개의 키(k=키 개수, n=슬롯 수)만 재배치하는 기법이다. 해시 공간을 원형(해시 링)으로 이어 붙이고 서버와 키를 같은 해시 함수로 링 위에 배치한다. 키는 자기 위치에서 시계 방향으로 처음 만나는 서버에 저장되므로, 서버가 추가·제거돼도 바로 인접한 구간의 키만 이동하고 나머지는 그대로다.

3. **Q. 해시 링에서 키가 저장될 서버는 어떻게 찾는가?**

   **A.** 키를 해시해서 링 위의 위치를 구한 뒤, 그 위치에서 시계 방향으로 돌며 처음 만나는 서버가 담당 서버다. 서버 위치를 정렬해 두면 이진 탐색으로 O(log n)에 찾을 수 있다.

4. **Q. 가상 노드는 왜 쓰는가? 개수를 늘리면 어떤 장단점이 있는가?**

   **A.** 기본 안정 해시는 서버가 추가·삭제되면 파티션(인접 서버 사이 구간) 크기를 균등하게 유지하기 어렵고, 키도 특정 서버에 몰릴 수 있다. 가상 노드는 실제 서버 하나를 링 위의 여러 위치에 흩뿌려 배치해서 이를 해결한다. 가상 노드가 많을수록 키 분포의 표준편차가 줄어 더 균등해지지만, 가상 노드 정보를 저장할 메타데이터 공간이 늘어난다. 그래서 균등함과 저장 비용 사이에서 적절한 수를 정해야 한다.

5. **Q. 서버가 추가/제거될 때 영향받는 키는 어떻게 찾는가?**

   **A.** 서버 추가 시에는 새 서버 위치에서 반시계 방향으로 이웃 서버를 만날 때까지의 키 범위가 새 서버로 옮겨진다. 서버 제거 시에도 제거된 서버 위치에서 반시계 방향으로 이웃 서버를 만날 때까지의 키 범위가 시계 방향 다음 서버로 옮겨진다. 그 외 키는 영향받지 않는다.
