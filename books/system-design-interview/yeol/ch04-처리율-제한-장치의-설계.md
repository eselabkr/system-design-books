> **책**: 가상 면접 사례로 배우는 대규모 시스템 설계 기초  
> **읽은 날짜**: 2026-10-17

## 한 줄 요약
: 과도한 트래픽으로부터 시스템을 보호하기 위해, 비즈니스 환경에 맞는 배치 위치(클라이언트/서버/게이트웨이/미들웨어)와 알고리즘을 선택하고 Redis 기반의 분산 동기화·성능 최적화·모니터링까지 고려하여 처리율 제한 장치를 설계한다.  

## 핵심 내용
### 처리율 제한의 2가지 접근 방식 (Hard vs Soft)
* **Hard 처리율 제한**: 요청 개수가 **임계치를 절대 넘어설 수 없음**
  - 특징: 한도 초과 즉시 엄격 차단 (HTTP 429)
  - 활용: 결제/인증 API, 악의적 공격 방어, 시스템 한계치 보호
* **Soft 처리율 제한**: 요청 개수가 **일시적으로 임계치를 넘어설 수 있음**
  - 특징: 일시적 트래픽 급증(Burst)이나 버퍼링을 허용하여 사용자 경험(UX) 개선
  - 활용: 일반 조회 API, SaaS 유료 서비스(초과 사용량 과금 허용 등)     

### 처리율 제한 장치 (Rate Limiter)
: 네트워크 시스템에서 클라이언트 또는 서비스가 보내는 트래픽의 처리율(Rate)을 제어하는 장치입니다. 특정 기간 내에 전송되는 클라이언트의 요청 횟수를 제한하여 시스템을 보호하고 안정성을 유지 
* 위치   
   * **클라이언트 측**: 위변조가 쉬워 신뢰하기 어렵기 때문에 보조 수단으로만 사용   
   * **서버 측**: API 서버 내부에서 직접 구현 (Filter/Interceptor 등)   
   * **API 게이트웨이 / 미들웨어 (가장 일반적)**: 백엔드 서버 앞단(Nginx, Spring Cloud Gateway, AWS API Gateway, Cloudflare 등)에 두어, 제한된 요청이
   백엔드 서버까지 도달하지 않도록 입구에서 차단한다. 
   * 그럼 어디에 두는 것이 좋은가? 
   : 회사의 현재 기술 스택(프로그래밍 언어와 서버의 구현 효율성, 캐시 서비스), 엔지니어링 인력, 우선순위, 목표에 따라 달라짐 

### 처리율 제한 장치 in 서버 측 vs 미들웨어
```
서버 측 구현:      클라이언트 → [ API 서버 (비즈니스 로직 + 제한 로직) ]
미들웨어 구현:     클라이언트 → [ 처리율 제한 미들웨어 ] → [ API 서버 ]
                                   │
                                   └─ 한도 초과 시 HTTP 429로 바로 응답 (API 서버까지 가지 않음)
```
- 미들웨어 동작 순서: ① 요청 수신 → ② 클라이언트별(사용자 ID, IP 등) 요청 횟수 확인 → ③ 한도 안이면 API 서버로 전달, 초과하면 429 반환
- 장점: 제한 로직이 서버 코드와 분리됨, 초과 요청이 서버 자원을 쓰지 않음, 서버가 여러 대여도 입구에서 일괄 제한

### 처리율 제한을 회피하는 방법
1. 클라이언트 측 캐시를 사용하여 API 호출 횟수를 줄인다.  
2. 처리율 제한의 임계치를 이해하고, 짧은 시간 동안 너무 많은 메시지를 보내지 않도록 한다. 
3. 예외나 에러를 처리하는 코드를 도입하여 클라이언트가 예외적 상황으로부터 우아하게(gracefully) 복구될 수 있도록 한다. 
4. 재시도 로직을 구현할 때는 충분한 백오프 시간을 둔다. 

### API 게이트 웨이 
: API 게이트웨이는 클라이언트(웹/앱)와 여러 백엔드 API 서버들 사이에 위치하여, 모든 요청을 가장 먼저 받아 검사하고 알맞은 API 서버로 전달해 주는 '통합 정문(단일 진입점)' 
기능 : 서버처리율 제한, SSL 종단, 사용자 인증, IP 허용 목록 관리 등을 지원하는 완전 위탁 관리형 서비스

```
                       [ 클라이언트 (스마트폰 앱) ]
                                  │
                     (오직 게이트웨이 주소 하나로만 요청)
                     https://api.baedal.com/...
                                  ▼
 ┌─────────────────────────────────────────────────────────────────┐
 │                     [ API 게이트웨이 서버 ]                         │
 │  1. 인증/인가 (로그인 토큰 유효한가?)                                  │
 │  2. 처리율 제한 (1초에 100번 넘게 요청한 악성 유저인가?)                  │
 │  3. 로깅 (누가 언제 어떤 요청을 보냈는가?)                              │
 │  4. 라우팅 (주소를 보고 어느 API 서버로 보낼지 결정!)                     │
 └───────┬────────────────────────┬────────────────────────┬───────┘
         │ /users/                │ /orders/               │ /payments/
         ▼                        ▼                        ▼
 [ 유저 API 서버 ]          [ 주문 API 서버 ]          [ 결제 API 서버 ]
 (Node.js로 개발)          (Spring으로 개발)         (Python으로 개발)

```
### 1단계: 문제 이해 및 설계 범위 확정
: 시스템 설계 전, 면접관과 질문을 통해 처리율 제한 장치의 목표와 제약 조건을 명확히 정의한다.

* **기능적 요구사항**:
  - 설정된 처리율을 초과하는 요청은 정확하게 차단한다.
  - 한도 초과 시 클라이언트에게 적절한 예외 응답(HTTP 429)을 반환한다.
  - 제한 기준을 유연하게 설정할 수 있어야 한다 (IP 주소, 사용자 ID 등).
* **비기능적 요구사항 (성능 및 안정성)**:
  - **낮은 지연시간(Low Latency)**: 제한 장치 때문에 실제 API 응답 속도가 느려지면 안 된다.
  - **메모리 효율성**: 가능한 한 적은 메모리를 사용해야 한다.
  - **분산 환경 지원**: 여러 서버와 프로세스에서 공유되어 일관되게 동작해야 한다.
  - **높은 결함 감내성(Fault Tolerance)**: 제한 장치에 장애가 발생해도 전체 시스템(API 서버)이 마비되면 안 된다.  

### 2단계: 개략적 설계안 제시 및 동의 구하기 
: 요청 횟수를 추적하는 카운터(Counter)를 추적 대상(IP, 사용자 등)별로 두고, 한도를 넘으면 요청을 거부하는 장단점이 서로 다른 `처리율 제한 알고리즘`을 사용한다.  

#### 처리율 제한 알고리즘
- 토큰 버킷
- 누출 버킷
- 고정 윈도 카운터
- 이동 윈도 로그
- 이동 윈도 카운터

* **토큰 버킷 (Token Bucket)**
  - 원리: 정해진 주기로 토큰이 채워지며, 요청마다 토큰 1개 소비.
  - 장점: 메모리 효율적, 구현 간단, 일시적인 트래픽 폭증(Burst) 수용 가능. (가장 널리 쓰임)
* **누출 버킷 (Leaky Bucket)**
  - 원리: 큐(Queue)에 요청을 쌓아두고 항상 일정한 속도로 꺼내서 처리.
  - 장점: 안정적인 출력 속도 보장. (전자상거래 결제, 메시지 큐 연동에 적합)
  - 단점: 단시간 트래픽 폭증 시 큐에 밀려 최신 요청들이 지연됨.
* **고정 윈도 카운터 (Fixed Window Counter)**
  - 원리: 정해진 시간 단위(예: 1분)로 카운터를 리셋하며 제한.
  - 장점: 구현이 가장 단순하고 메모리 사용량 적음.
  - 단점: 윈도 경계 시간대(예: 00:59 ~ 01:01)에 트래픽이 몰리면 한도의 최대 2배까지 통과할 수 있음.
* **이동 윈도 로그 (Sliding Window Log)**
  - 원리: 모든 요청의 타임스탬프를 로그(Redis Sorted Set 등)에 기록하여 현재 기준 과거 윈도 내 요청 개수를 정확히 계산.
  - 장점: 어느 시점에든 매우 정밀한 처리율 제한 가능.
  - 단점: 거부된 요청의 타임스탬프까지 다 보관해야 해서 메모리 낭비가 심함.
* **이동 윈도 카운터 (Sliding Window Counter)**
  - 원리: 고정 윈도의 메모리 효율성과 이동 윈도 로그의 정밀함을 결합한 추정 알고리즘.
  - 장점: 메모리를 거의 쓰지 않으면서도 경계선 트래픽 폭증 문제를 훌륭하게 완화.  

#### 개략적 아키텍처 (카운터 저장소: Redis 등)
  * **데이터베이스(RDB) 대신 인메모리 캐시(Redis)를 쓰는 이유**:
    - 디스크 기반 DB는 읽기/쓰기가 너무 느려 모든 API 요청마다 카운터를 갱신하면 DB가 병목이 됨.
    - 메모리 기반 저장소인 **Redis**는 빠른 속도(`O(1)`)와 만료 시간(`TTL`), 그리고 원자적 증가/감소 연산(`INCR`, `EXPIRE`)을 지원하므로 카운터 저장소로 최적임.

#### 처리율 제한 규칙

#### 처리율 한도 초과 트래픽의 처리 (HTTP 429 응답 헤더)

#### 분산 환경에서의 처리율 제한 (경쟁 조건, 동기화)

  * 정의한 `처리율 제한 규칙`이 효과적이다. 

### 4단계: 마무리
: 처리율 제한을 구현하는 여러 알고리즘의 장단점, 알고리즘을 구현하는 아키텍처, 분산환경에서의 처리율 제한 장치, 성능 최적화, 모니터링에 대해 다룸.

## 인상 깊은 구절

> 성능 최적화는 시스템 설계 면접의 단골 주제다. 
> 첫 번째로, 지연시간을 줄이기 대부분 클라우드 서비스 사업자는 세계 곳곳 `에지 서버(edge server)`를 심어놓고 있다. 
> 두 번째로, 제한 장치 간에 데이터를 동기화할 때 `최종 일관성 모델 (eventual consistency model)`을 사용하는 것이다. 
>
> - p.72 
**왜 인상 깊었나:**
단순히 여러 서버 간 데이터는 무조건 빠르게 업데이트해서 일치하는 것이 좋을 줄 알았는데, 잘못 알고 있는 부분이였다. 처리율 제한은 100% 정밀할 필요가 없으므로, 엄격한 실시간 동기화 대신 비동기 동기화를 채택하여 응답 속도와 처리량(Throughput)을 극대화한 것.

> 분산 환경에서 동기화 이슈를 해결하기 위해 고정 세션은 규모면에서 확장 가능하지도 않고 유연하지 않기 때문에, 레디스와 같은 중앙 집중형 데이터 저장소를 쓰는 것이다. 
>
> — p. 71 
**왜 인상 깊었나:**
레디스에 대해 전혀 몰랐었는데, 이번 기회를 통해 레디스의 역할, 중요성에 대해서 알게되었고 왜 많이 쓰이고 있는지 이유도 알 수 있었다. 

## 면접 예상 질문
1. **Q. 처리율 제한 장치가 제대로 동작하는지 모니터링으로 무엇을 확인하는가?**

  **A.** 채택한 처리율 제한 알고리즘이 효과적인지, 정의한 처리율 제한 규칙이 효과적인지를 확인한다.

2. **Q. 처리율 제한 장치는 왜 필요한가?**

   **A.** 클라이언트나 서비스가 보내는 요청 횟수를 제한해서 시스템을 보호하고 안정성을 유지하기 위해서다. DoS 같은 과도한 요청으로 인한 자원 고갈과 서버 과부하를 막고, 외부 API 호출 과금 같은 비용도 줄일 수 있다.

3. **Q. 처리율 제한 장치는 클라이언트, 서버, 미들웨어 중 어디에 두는 게 좋은가?**

   **A.** 클라이언트 측은 요청이 위변조되기 쉬워 신뢰하기 어려우므로 보조 수단으로만 쓴다. 서버 측(Filter/Interceptor)은 알고리즘 선택이 자유롭고, API 게이트웨이나 미들웨어는 입구에서 차단해 백엔드 서버 자원을 아낄 수 있다. 정답은 없고 회사의 기술 스택, 엔지니어링 인력, 우선순위, 목표에 따라 달라진다고 답하고, 상황별 근거를 들어 선택한다.

4. **Q. 분산 환경에서 여러 서버가 처리율 제한을 할 때 동기화는 어떻게 하는가?**

  **A.** 고정 세션은 규모 면에서 확장 가능하지도 유연하지도 않아서, Redis 같은 중앙 집중형 데이터 저장소를 공유한다. 또 제한 장치 간 데이터는 최종 일관성 모델로 동기화한다. 처리율 제한은 100% 정밀할 필요가 없으므로 엄격한 실시간 동기화보다 비동기 동기화가 응답 속도와 처리량 면에서 유리하다.

5. **Q. 클라이언트 입장에서 처리율 제한에 걸리지 않으려면 어떻게 해야 하는가?**

  **A.** 클라이언트 측 캐시로 API 호출 횟수를 줄이고, 임계치를 이해해서 짧은 시간에 너무 많은 요청을 보내지 않는다. 예외 처리 코드를 두어 우아하게 복구하고, 재시도 로직에는 충분한 백오프 시간을 둔다.
