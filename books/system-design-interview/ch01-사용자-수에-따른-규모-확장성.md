## 한 줄 요약

시스템의 규모를 확장하는 것은 지속적이고 반복적인 과정이다.

## 핵심 내용

### 수직적 규모 V.S. 수평적 규모 확장 
- 수직적 규모 확장(Scale up) : 서버 한 대에 더 고사양의 자원(CPU, 램 등)을 추가하는 방식이다.
   - 단순하지만 한 대의 서버에 추가할 수 있는 자원에는 한계가 있다.
   - 장애 시 대비책(failover)이나 다중화 방안이 없어, 서버가 죽으면 서비스 전체가 중단된다(SPOF).
- 수평적 규모 확장(Scale out) : 서버 대수를 늘려 성능을 높이는 방식이다.
   - 로드밸런서로 트래픽을 여러 서버에 분산하고, 한 서버가 죽어도 나머지 서버로 서비스를 이어갈 수 있다.
   - 대규모 애플리케이션에 적합하다.
- 데이터베이스의 확장 기법 (복제와 샤딩은 Scale up의 하위 방식이 아니라 DB 계층을 확장하는 기법이다)
   - 복제 : 같은 데이터를 여러 서버에 저장한다. 보통 master-slave 구조로, 쓰기는 master, 읽기는 slave가 담당한다.
   - 샤딩 : 샤딩 키에 따라 데이터를 여러 샤드에 나눠 저장한다. DB에 수평적 규모 확장을 적용한 방식이다.

### 데이터베이스의 다중화 장점
1. 성능 향상 : 읽기 연산이 여러 slave 서버로 분산되어 병렬로 처리된다. (쓰기는 master에서만 처리한다)
2. 안정성(Reliability) : 일부 DB 서버가 파괴되어도 데이터가 다른 서버에 복제되어 있어 보존된다.
3. 가용성(Availability) : 한 DB 서버에 장애가 나도 다른 서버의 데이터로 서비스를 계속할 수 있다.

### 배포 환경
- 개발(Development) 환경: 개발자들이 코드를 작성하고 소프트웨어를 만드는 초기 작업 환경
- 스테이징(Staging) 환경: 실제 서비스에 배포하기 직전, 내부적으로 오류가 없는지 최종 테스트를 진행하는 환경
- 프로덕션(Production) 환경: 실제 사용자가 접속하여 서비스를 이용하고 있는 라이브 서비스 환경

### 캐시 사용의 일관성(Consistency) 유지 어려움
원본 데이터를 변경시에 캐시 내의 사본과의 일관성을 유지하는 것이 어렵다. 저장소의 원본 갱신 연산과 캐시 갱신 연산이 단일 트랜잭션으로 처리되지 않고 캐시의 만료 기간이 지나치게 길다면 일관성은 깨질 수 밖에 없음. 

### 배운 내용 정리 
1. 웹 계층은 무상태 계층으로
2. 모든 계층에 다중화 도입
3. 가능한 한 많은 데이터를 캐시할 것 
4. 여러 데이터 센터를 지원할 것
5. 정적 콘텐츠는 CDN을 통해 서비스할 것 
6. 데이터 계층은 샤딩을 통해 그 규모를 확장할 것
7. 각 계층은 독립적 서비스로 분할할 것 
8. 시스템을 지속적으로 모니터링하고, 자동화 도구들을 활용할 것

## 면접 예상 질문

1. **Q. 수직적 규모 확장과 수평적 규모 확장의 차이는 무엇이고, 각각 언제 선택하는가?**
   **A.** 수직적 규모 확장(Scale up)은 서버 한 대의 CPU, 메모리 같은 사양을 올리는 방식이다. 구조가 단순해 트래픽이 적을 때 적합하지만, 하드웨어 증설에는 한계가 있고 서버가 한 대뿐이라 장애가 나면 서비스 전체가 멈춘다(SPOF). 수평적 규모 확장(Scale out)은 서버 대수를 늘리고 로드밸런서로 트래픽을 분산하는 방식이다. 확장 한계가 사실상 없고 한 서버가 죽어도 나머지가 요청을 처리하므로 대규모 서비스에 적합하다. 대신 웹 계층을 무상태로 설계하고 데이터 일관성을 관리해야 하는 등 복잡도가 올라간다.

2. **Q. 웹 계층을 무상태(stateless)로 만들어야 하는 이유는 무엇인가?**
   **A.** 세션 같은 상태 정보를 웹 서버에 저장하면 같은 사용자의 요청이 항상 같은 서버로 가야 한다. 이를 위해 로드밸런서가 고정 세션(sticky session)을 지원해야 하고, 서버를 추가하거나 제거하기 어려우며, 서버 장애 시 그 서버의 세션이 사라진다. 상태 정보를 Redis, NoSQL 같은 공유 저장소로 옮기면 어떤 웹 서버든 요청을 처리할 수 있다. 그 결과 트래픽에 따라 서버를 자동으로 늘리고 줄이는 오토스케일링이 쉬워진다.

3. **Q. 캐시를 도입할 때 고려해야 할 점은 무엇인가?**
   **A.** 첫째, 읽기는 잦고 갱신은 드문 데이터에 적합하다. 둘째, 캐시는 휘발성 메모리이므로 중요한 데이터는 반드시 영속 저장소에 둔다. 셋째, 만료 기간(TTL)을 적절히 정한다. 너무 짧으면 DB 조회가 잦아지고, 너무 길면 원본과 달라진 오래된 데이터를 반환한다. 넷째, DB 갱신과 캐시 갱신은 하나의 트랜잭션으로 묶이지 않으므로 일관성이 깨질 수 있다. 원본 변경 시 캐시를 무효화하는 식으로 대응한다. 다섯째, 캐시 서버 한 대가 SPOF가 되지 않도록 여러 대를 둔다. 여섯째, 메모리가 가득 찼을 때 무엇을 버릴지 방출 정책(LRU, LFU, FIFO)을 정한다.

## AI 활용 기록

| 막힌 곳 | 어떻게 풀었나 | 검증 |
| --- | --- | --- |
| 웹 서버 응답은 HTML, JSON 말고 또 무엇이 있나 | SSR 브라우저 렌더링용 HTML, REST API 직렬화 포맷인 JSON과 XML, MSA 통신용 바이너리 직렬화 포맷인 Protocol Buffers(gRPC 프레임워크에서 사용), 실시간 스트리밍용 SSE와 WebSocket 등으로 나뉜다. | 🟢 검증 완료 (HTML, JSON, XML, SSE, WebSocket은 MDN 문서와 일치함. gRPC와 Protocol Buffers는 MDN에 없으므로 grpc.io, protobuf.dev 공식 문서로 확인 필요. 마이크로서비스 통신에는 gRPC, AI 채팅에는 스트리밍 응답이 자주 쓰임) |
| 서버 언어별 특장점과 요즘 많이 쓰는 언어 | 엔터프라이즈 표준인 Java(Spring), 높은 생산성과 AI·데이터 생태계가 강점인 Python(Django, FastAPI), 이벤트 루프 기반 비동기 I/O로 I/O 병목에 강한 Node.js, 고루틴 기반 고도 동시성 처리가 가능한 Go(인프라 표준) 언어 등이 있다. | 🟢 검증 완료 (업계 트렌드와 일치함. 국내는 Java/Spring이 압도적이며 트래픽이 몰리는 인프라는 Go로 작성되는 추세임) |
| JSON은 왜 간결하고 XML, YAML, md와는 어떻게 다른가 | XML은 명시적 태그로 오버헤드가 크고 JSON은 Key-Value 기반의 REST API 표준이다. YAML은 들여쓰기 기반으로 선언적 인프라 설정 표준이며 md는 텍스트 서식용 마크업이다. | 🟢 검증 완료 (공식 스펙과 일치함. JSON이 훨씬 가볍고 Dockerfile은 독자적인 문법을 쓰며 compose에서만 YAML을 사용함) |
| NoSQL 4가지 분류의 특징 | 키로 값을 바로 찾는 Key-Value(Redis처럼 In-Memory 기반이면 매우 빠름), BSON 기반 Schema-less인 Document(MongoDB), 대규모 쓰기에 최적화된 Wide-Column(Cassandra), N:M 다대다 관계 탐색에 최적화된 Graph(Neo4j)로 나뉜다. | 🟢 검증 완료 (데이터베이스 실무 내용과 일치함. 특히 세션/캐시에 Redis, 대량 쓰기에 Cassandra를 쓴다는 것은 정석임) |
| 데이터가 아주 많을 때 왜 NoSQL이 유리한가 (RDB가 형식이 정해져 더 많이 저장할 수 있을 것 같았다) | RDBMS는 분산 트랜잭션 및 다중 노드 JOIN 비용이 커서 수평 확장이 어렵다. NoSQL은 복잡한 JOIN을 포기한 대신 Shard Key 기반으로 데이터를 파티셔닝하여 Scale-out(수평 확장) 효율을 극대화한다. | 🟢 검증 완료 (RDB는 분산 환경에서 ACID 유지가 매우 비싼 반면 NoSQL은 서버를 추가하는 방식의 확장에 유리하게 설계됨. 단, NoSQL도 확장에 한계가 없는 것은 아니고, RDB도 Vitess, Citus 같은 도구로 샤딩할 수 있음) |
| slave 서버는 왜 쓰기를 하면 안 되나 | Multi-Master 구조는 동시 변경 시 충돌 해결 및 분산 합의가 복잡하다. 쓰기를 단일 Master로 제한해 WAL을 직렬화하고 Replica는 그 변경을 복제(보통 비동기, 필요하면 동기·반동기)하여 읽기 전용으로 분산 처리하는 것이 유리하다. | 🟢 검증 완료 (다중 마스터 구조도 있지만 충돌 해결이 크게 복잡해져 쓰기를 1곳으로 강제해 순서를 보장함) |
| 캐시에 무엇을 저장할지는 누가, 어떤 기준으로 정하나 | 백엔드 코드 레벨에서 Cache-Aside 패턴 등으로 직접 제어한다. Read-to-Write 비율이 높거나 연산 비용이 큰 데이터를 대상으로 하며, Redis 단에 LRU 등의 방출 정책을 설정하여 메모리 한계를 방어한다. | 🟢 검증 완료 (실무 패턴과 일치함. 백엔드 개발자가 조회가 잦고 연산이 무거운 로직 앞단에 직접 캐시 패턴을 구현함) |
