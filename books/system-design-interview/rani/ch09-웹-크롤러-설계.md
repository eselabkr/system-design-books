## 한 줄 요약
웹 크롤러는 시작 URL부터 링크를 따라 웹 페이지를 자동으로 수집하며, 중복 제거와 URL 우선순위 관리 등을 통해 효율적이고 안정적으로 콘텐츠를 수집하는 시스템이다.

## 핵심 내용

# 웹 크롤러
= 로봇 or 스파이더
: 웹에 새로 올라오거나 갱신된 콘텐츠를 찾아내는 목적을 가진 검색 엔진에서 널리 쓰는 기술
몇 개 웹 페이지에서 시작하여 그 링크를 따라 나가면서 새로운 콘텐츠를 수집
* 콘텐츠 ex) 웹 페이지, 이미지, 비디오, PDF 파일 등

| 명칭 | 설명 |
|---|---|
| 로봇(Robot) | 웹페이지를 자동으로 방문하고 정보를 수집하는 프로그램 |
| 스파이더(Spider) | 웹페이지의 링크를 따라 이동하며 정보를 수집하는 프로그램 |
| 웹 크롤러(Crawler) | 로봇, 스파이더와 같은 의미로 사용되는 용어 |

# 크롤러의 이용
- 검색 엔진 인덱싱 : 웹 페이지를 모아 검색 엔진을 위한 로컬 인덱스를 만듬 ex) Googlebot
- 웹 아카이빙 : 나중에 사용할 목적으로 장기 보관하기 위해 웹에서 모음 ex) 미국 국회 도서관, EU 웹 아카이브
- 웹 마이닝 : 인터넷에서 유용한 지식을 도출해 내는 것 ex) 주주 총회 자료, 연차 보고서 등에 사용
- 웹 모니터링 : 저작권, 상표권 참해 사례 모니터링 ex) 디지마크사

# 웹 크롤러의 기본 알고리즘
1. 입력 [ URL 집합 ] → 해당 모든 URL의 모든 웹페이지를 다운로드
2. 다운받은 웹 페이지에서 URL 추출
3. 추출된 URL들을 다운로드할 URL 목록에 추가하고 위의 과정을 처음부터 반복함

But, 규모 확장성을 갖는 웹 크롤러 설계는 어렵고 이렇게 단순하게 동작하지 않음

# 웹 크롤러 만족 속성
- 규모 확장성 : 규모가 크므로 병행성을 활용해 효과적으로 진행하기
- 안정성 : 웹에는 함정이 많아 비 정상적 입력이나 환경에 잘 대응해야 함
- 예절 : 짧은 시간 너무 많은 요청을 보내서는 안된다
- 확장성 : 새로운 형태의 콘텐츠를 지원하기 쉬워야 함. 전체 시스템 새로 설계 X

# 요구사항에 맞게 설계 예시
- 일일 웹 다운로드 수 : 10억
- QPS = 10억 / 30일 / 24시간 / 3600초 = 약 400 페이지/초 
- 최대 QPS = 2 x QPS = 800
- 웹 페이지 크기 평균 = 500k
- 10억 페이지 x 500k = 500TB/월 (2의 제곱수)
- 데이터 5년 보관 = 500TB x 12 x 5 = 30PB

# HTML 다운로더
인터넷에서 웹 페이지를 다운로드 하는 컴포넌트
다운로드할 페이지의 URL은 미수집 URL 저장소가 제공한다.

| 구분 | 설명 |
|---|---|
| 미수집 URL 저장소 | 아직 수집하지 않은 웹 페이지의 URL을 관리하는 저장소 |
| HTML 다운로더 | URL에 접속하여 웹 페이지의 HTML을 다운로드하는 컴포넌트 |
| 동작 과정 | 미수집 URL 저장소 → HTML 다운로더 → HTML 다운로드 |

# 도메인 이름 변환기
웹 페이지 다운로드시 URL을 IP 주소로 변환하는 절차가 필요.
ex) HTML 다운로더는 도메인 이름 변환기 사용하여 IP 주소 찾음
예시) www.wikipedia.org → 198.35.26.96 

# 콘텐츠 파서
웹 페이지 다운시 파싱과 검증 절차 거침
Why? 이상한 웹페이지는 문제 일으킬수 있고 저장 공간 낭비가 심함

# 중복 콘텐츠인가?
같은 콘텐츠를 여러번 저장하게 될수 있는데, 데이터 중복을 줄이고 데이터 처리에 소요되는 시간을 줄인다
간단한 방법 : 두 문서를 문자열로 비교
효과적 방법 : 웹 페이지의 해시 값을 비교

# 콘텐츠 저장소
HTML 문서를 보관하는 시스템
저장소를 구현할 기술 고를때 고려해야 할 예시 : 데이터 유형, 크기, 저장소 접근 빈도, 데이터 유효기간 등

ex) 데이터 많으므로 대부분 콘텐츠는 디스크에 저장
인기있는 콘텐츠는 메모리에 두어 접근 지연시간을 줄임

# URL 추출기
HTML 페이지를 파싱하여 링크 추출. 상대 경로는 절대 경로로 변환
- 상대경로 ex) /wiki/Cong_Weixi
- 절대경로 ex) https://en.wikipedia.org/wiki/Cong_Weixi

# URL 필터
특정 URL을 크롤링 대상에서 제외

ex) 
- 특정한 콘텐츠 타입이나 파일 확장자 URL
- 접속 오류 URL
- 접근 제외 목록에 포함된 URL

# 이미 방문한 URL인가?
블룸 필터나 해시 테이블 처럼,
이미 방문하거나 미수집 URL을 추적할 수 있는 자료 구조를 사용해서 서버 부하를 줄이고 무한 루프 방지함

# URL 저장소
이미 방문한 URL 보관하는 저장소

# 웹 크롤러 작업 흐름
(그림 9-4 를 그려보자)

1. 시작 URL들을 미수집 URL 저장소에 저장하고, HTML 다운로더가 URL 목록 가져옴
2. HTML 다운로더는 도메인 이름 변환기로 해당 IP를 찾아 웹페이지 다운받고
3. 콘텐츠 파서는 다운된 HTML 페이지를 파싱하여 검증 작업 함
4. 중복 콘텐츠인지 체크하고 있으면 버리고 없으면 저장소에 저장 후 URL 추출기로 보냄
5. URL 추출기는 링크를 골라 URL 필터로 전달해 필터링을 하고, 중복 URL 판별 진행
6. 처리한 URL인지 체크하고 있으면 버리고 없으면 URL 저장소와 미수집 URL 저장소에 전달

# DFS (Depth-First-Search)
깊이 우선 탐색법
* 문제점 : 웹 크기가 클 경우 가늠이 어렵다

# BFS (Breadth-First-Search)
너비 우선 탐색법
FIFO 큐 사용
큐의 한쪽으로 탐색할 URL을 넣고, 다른 한쪽으로 꺼내기만 한다

* 문제점
- 대부분 링크는 같은 서버로 되돌아 가는데, 병렬 처리시 수많은 요청으로 과부하에 걸리게 되어 예의없는 크롤러로 간주됨
- 처리 순서를 공평하게 해서 URL 간 우선순위 두지 않음
(문제인 이유 : 모든 웹페이지가 같은 수준,품질 등 같은 수준의 중요성을 갖지 않는데 페이지 순위, 사용자 트래픽 양, 업데이트 빈도 등 우선 순위를 구별하는게 좋음)

(그림 9-5 자리)

# 미수집 URL 저장소 (2차)
우선순위 구별 해결 가능
- 예의를 갖춘 크롤러
- URL 사이의 우선순위와 신선도 구별

# 예의
짧은 시간 안에 너무 많은 요청 X
안정장치가 없는 경우, 웹 사이트를 마비시킬수 있음.

원칙 : 동일 웹 사이트의 경우 한번에 한 페이지만 요청하며, 같은 웹사이트의 경우에는 시간 차를 두고 실행.
호스트명과 다운로드를 수행하는 작업 스레디 사이의 관계를 유지

- 큐 라이터 : 같은 호스트의 URL은 같은 큐로 가게 보장
- 매핑 테이블 : host명 ↔ 큐 관계 보관
- FIFO 큐 : 같은 호스트의 URL은 같은 큐에 보관
- 큐 선택기 : 큐에서 URL을 다운로드하게 작업 스레드에 전달
- 작업 스레드 : 전달된 URL을 다운로드하고, 순차적으로 처리하나 지연시간을 둘수 있음.

# 우선순위
중요한 홈페이지 먼저 수집
ex) 페이지랭크, 트래픽 양, 갱신 빈도

# 순위결정장치
URL 정하는 컴포넌트로 URL을 입력받아 우선순위를 계산

* 용어 정리
큐 : 우선순위별로 큐 할당. 우선 순위가 높으면 선택 확률 큼
큐 선택기 : 임의 큐에서 처리할 URL을 꺼냄.
전면 큐 : 우선순위 결정 과정을 처리
후면 큐 : 크롤러가 예의 바르게 동작하게 보증

# 신선도
웹 페이지는 자주 추가/삭제/변경이 이루어지는데,
이미 다운로드 했어도 재수집 작업을 거침
ex) 웹 페이지 변경 이력 활용

# HTML 다운로더 (2차)

ex) Robots.txt // 로봇 제외 프로토콜

## 면접 예상 질문
1. **Q. 웹 크롤링에서 DFS와 BFS의 차이는 무엇인가요?**  
   **A.** DFS는 깊이 우선 탐색으로, 하나의 링크를 따라 최대한 깊게 탐색한 후 다른 경로로 이동합니다. 웹의 깊이를 예측하기 어려워 크롤링에 적합하지 않을 수 있습니다.  
   BFS는 너비 우선 탐색으로, FIFO 큐를 사용하여 가까운 링크부터 순서대로 탐색합니다. 다만 기본 BFS는 URL의 중요도에 따른 우선순위를 고려하지 않으며, 같은 서버에 요청이 집중되어 과부하가 발생할 수 있습니다.

2. **Q. 웹 크롤러에서 미수집 URL 저장소는 어떤 역할을 하나요?**  
   **A.** 아직 방문하지 않은 URL을 관리하고, HTML 다운로더에 수집할 URL을 제공합니다. 대규모 크롤러에서는 URL의 우선순위와 서버별 요청 간격을 관리하여 효율적이고 예의 바른 크롤링을 수행하도록 합니다.

3. **Q. 웹 크롤러에서 중복 콘텐츠와 중복 URL은 어떻게 처리하나요?**  
   **A.** 중복 콘텐츠는 웹 페이지의 해시 값을 비교하여 판별하고, 중복 URL은 해시 테이블이나 블룸 필터 등을 활용하여 확인합니다. 이를 통해 불필요한 다운로드와 저장 공간 낭비를 줄이고, 반복적인 크롤링을 방지합니다.

4. **Q. 웹 크롤러에서 안정성과 예절을 확보하려면 어떻게 해야 하나요?**  
   **A.** 안정성을 위해 잘못된 HTML이나 응답 오류에 대한 예외 처리를 구현하고, 실패한 요청은 재시도 정책을 적용합니다. 예절을 위해 robots.txt를 준수하고, 동일 서버에 짧은 시간 동안 과도한 요청을 보내지 않도록 요청 간격과 동시 요청 수를 제한합니다.
