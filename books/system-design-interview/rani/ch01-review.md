### 1. 로그인 요청은 서버 A에서 처리하고, 다음 요청은 서버 B로 들어왔을 때 로그인 상태를 어떻게 유지하는지 설명하기

답변) 서버 A와 서버 B가 각각 세션 정보를 관리한다면 서버 A에서 로그인한 사용자가 서버 B로 요청했을 때 로그인 상태를 유지하지 못할 수 있다.

이를 해결하기 위해 Redis 같은 공유 저장소에 세션 정보를 별도로 관리하면 무상태 웹 계층을 구성할 수 있다.

사용자가 로그인하면 브라우저는 세션 ID를 쿠키에 저장하고, 이후 서버 B로 요청할 때 해당 쿠키를 전달한다. 서버 B는 세션 ID를 이용해 Redis에서 로그인 정보를 조회하여 로그인 상태를 유지할 수 있다.

AI Log)

- 무상태 웹 계층은 웹 서버 자체에 사용자 상태를 저장하지 않고 독립적으로 요청을 처리할 수 있는 구조이다.
- 서버 A가 서버 B로 세션 정보를 직접 전달하는 것이 아니라, 브라우저가 세션 ID를 전달하고 서버 B가 공유 저장소에서 조회한다.
- Redis는 캐시뿐 아니라 공통 세션 저장소로도 활용할 수 있다.

### 2. 데이터를 삭제했을 때 어떤 일이 생기는지를 예로 들어 DB 복제와 백업의 차이 설명하기

답변) DB 복제는 운영 DB의 데이터를 다른 DB에도 지속적으로 반영하는 방식으로, 가용성을 높이거나 조회 부하를 분산하기 위한 목적으로 사용한다.

운영 DB에서 데이터를 삭제하면 복제 DB에도 삭제 내용이 반영되기 때문에 일반적인 DB 복제만으로는 삭제된 데이터를 복구하기 어렵다.

반면 DB 백업은 특정 시점의 데이터를 별도로 보관하는 방식으로, 운영 DB에서 데이터를 삭제하거나 문제가 발생했을 때 이전 상태로 복구하기 위한 목적으로 사용한다.

AI Log)
**예시: 오전 10시에 데이터 100개가 있었고, 오전 11시에 20개를 삭제한 경우**

| 구분 | DB 복제 | DB 백업 |
| --- | --- | --- |
| 주요 목적 | 가용성 및 조회 부하 분산 | 데이터 복구 |
| 데이터 변경 | 지속적으로 반영 | 백업 시점의 데이터 보관 |
| 데이터 삭제 | 복제 DB에도 삭제 반영 | 기존 백업본은 유지 |
| 삭제 데이터 복구 | 일반적인 복제만으로는 어려움 | 삭제 전 백업으로 복구 가능 |

- 처음에는 DB 복제를 특정 시점의 데이터를 그대로 보관하는 것으로 이해했으나, 이는 백업에 가까운 개념이다.
- DB 복제는 운영 DB의 변경 사항이 복제 DB에도 반영되며, 반영 시점에는 지연이 발생할 수 있다.
- 일반적인 주 DB와 복제 DB 구조에서는 복제 DB를 읽기 전용으로 운영하며, 운영 DB의 변경 사항을 복제 DB에 전달한다.
- DB 복제와 백업은 데이터를 복사한다는 공통점이 있지만 목적과 데이터 변경 방식에 차이가 있다.

### 3. 현재 업무에서 사용하는 캐시가 어떤 캐시인지, 무엇을 저장하고 언제 갱신되는지 확인하기

답변) 현재 업무에서는 별도로 도입하여 사용하는 캐시 시스템을 확인하지 못했다.
지난번 따로 질문할때, 쿠키와 캐시를 혼동하여 잘못 설명진행하였음.

AI Log)
쿠키는 세션 ID 등의 정보를 브라우저에 저장하고 요청할 때 서버에 전달하는 용도로 사용한다.
반면 캐시는 자주 사용하는 데이터를 임시 저장하여 반복적인 조회나 연산을 줄이고 응답속도를 개선하기 위한 기술이다.

| 구분 | 쿠키 | 캐시 |
| --- | --- | --- |
| 목적 | 사용자 식별 및 상태 유지 | 데이터 재사용 및 성능 개선 |
| 저장 대상 | 세션 ID, 사용자 설정 등 | 조회 결과, 이미지, API 응답 등 |
| 저장 위치 | 브라우저 | 브라우저, 서버, CDN 등 |
| 사용 예시 | 로그인 상태 유지 | 반복적인 DB 조회 감소 |

- 쿠키와 캐시는 모두 데이터를 저장할 수 있지만 사용 목적이 다르다.
- Redis 같은 별도의 캐시 시스템을 사용하지 않더라도 브라우저 캐시나 DB 내부 캐시가 사용될 수 있다.
- 현재 업무에서 어떤 캐시를 사용하는지, 무엇을 저장하고 언제 갱신하는지는 추가 확인이 필요하다.
