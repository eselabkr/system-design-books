## 한 줄 요약

설명한 대상과 개념은 다르지만, 규모가 커지면 확장이 필요해지는데 성능이 좋은 것을 쓰는 방법과 여러 개로 나누어 관리해서 부하를 분산하는 방법이 있다.

## 핵심 내용

### 서버 규모 확장

처음에는 웹, 앱, DB, 캐시 등을 하나의 서버에서 시작할 수 있지만 규모가 커지면 결국 확장이 필요해진다.

수직적 확장은 CPU나 RAM처럼 서버 자체의 성능을 높이는 방법이고, 수평적 확장은 서버를 여러 개로 늘려 부하를 나누는 방법이다. 수직적 확장은 성능을 계속 높이는 데 한계가 있기 때문에 규모가 커질수록 수평적 확장이 필요해진다.

### 로드밸런서와 DB 다중화

서버를 여러 개로 늘리면 요청이 한 서버에 몰리지 않도록 나눠줘야 하는데, 이 역할을 로드밸런서가 한다.

DB도 여러 개로 구성할 수 있다. 주 DB는 저장, 수정, 삭제 같은 쓰기 작업을 담당하고 부 DB는 주로 조회를 담당한다. 역할을 나누면서 성능을 높이고 하나의 서버에 문제가 생겼을 때도 대응할 수 있다.

### 캐시와 CDN

캐시는 자주 사용하는 데이터를 저장해두고 다시 사용하는 방식이다. 매번 DB에서 같은 데이터를 가져오는 횟수를 줄여 응답 속도를 높이고 DB의 부담도 줄일 수 있다.

CDN은 이미지, CSS, JS 같은 콘텐츠를 여러 위치에 저장해 사용자에게 전달한다. 캐시와 CDN 모두 저장된 데이터를 사용하기 때문에 데이터의 만료 시점도 중요하다.

### 무상태 웹 계층

웹 서버가 특정 사용자의 상태 정보를 직접 가지고 있으면 해당 사용자의 요청이 같은 서버로 계속 전달되어야 한다. 상태 정보를 별도의 저장소에 두면 어떤 웹 서버로 요청이 들어와도 필요한 정보를 가져와 처리할 수 있다. 이렇게 웹 서버와 상태 정보를 분리하면 서버를 추가하거나 줄이기도 쉬워진다.

### 데이터 센터

서비스 규모가 커지면 여러 지역에 데이터 센터를 둘 수 있다. 사용자의 위치에 따라 가까운 데이터 센터로 요청을 보내고, 특정 데이터 센터에 장애가 발생하면 다른 데이터 센터로 트래픽을 보낼 수도 있다. 여러 데이터 센터가 서로 다른 위치에 있을 때 같은 서비스를 제공하기 위해서는 데이터 동기화가 필요하다.

### 메시지 큐

메시지 큐는 처리할 작업을 바로 실행하지 않고 큐에 저장해두었다가 처리하는 방식이다.

메시지를 보내는 쪽과 처리하는 쪽을 분리할 수 있어서 비동기 작업에 사용할 수 있고, 각 서비스가 직접 연결되는 것을 줄일 수 있다.

### 로그, 메트릭, 자동화

로그는 시스템에서 발생한 작업이나 오류를 기록하고 확인하는 데 사용한다.

메트릭은 서버나 서비스의 상태를 수치로 확인하기 위한 정보이고, 자동화는 빌드, 테스트, 배포 같은 반복적인 작업을 자동으로 처리하는 데 사용한다.

시스템 규모가 커질수록 직접 확인하고 처리해야 할 대상도 많아지기 때문에 이런 기능들의 필요성도 커진다.

### DB 규모 확장과 샤딩

DB도 서버와 마찬가지로 수직적, 수평적으로 확장할 수 있다. 샤딩은 많은 데이터를 여러 DB에 나누어 저장하는 방법이다. 어떤 데이터를 어느 샤드에 저장할지 결정하는 샤딩 키가 중요하다.

다만, 샤딩은 데이터를 여러 개로 나누어 저장하는 방식이기 때문에 데이터가 여러 샤드에 나뉘어 있는 경우 JOIN하기 어려워지는 문제도 있다.

### 전체적으로

이번 장을 읽으면서 시스템 규모 확장은 처음부터 모든 걸 크게 만드는 게 아니라 규모가 커지면서 생기는 문제를 하나씩 해결해 나가는 과정이라고 이해했다.

단일 서버에서 시작해서 규모가 커지면 서버를 여러 개로 늘리고, 로드밸런서나 DB 다중화, 캐시, CDN, 샤딩 등을 적용하게 된다. 각각 적용되는 대상이나 방법은 다르지만 전체적으로 보면 규모가 커졌을 때 어떻게 확장할 것인지에 대한 내용이었고, 수직적인 확장보다는 수평적인 확장에 초점이 맞춰져 있었다.

그 외에도 무상태 웹 계층, 메시지 큐, 로그, 메트릭, 자동화 등 규모가 커지면서 필요한 여러 개념들이 같이 나왔는데, 이 부분은 아직 개념이 부족해서 더 알아봐야겠다.

## 인상 깊은 구절

> 수직적 규모 확장 vs 수평적 규모 확장, 확장은 지속적이고 반복적인 과정
>
> — p.5, 29

**왜 인상 깊었나:**

전체적인 1장 내용을 확인해 보았을 때, 적용되는 개념은 단일 서버, 로드밸런서, DB, 캐시, 샤딩 등 계속 바뀌었지만 반복적으로 강조하는 내용 중 하나가 수직적, 수평적 확장에 대한 내용이었다.

시스템의 확장은 지속적이고 반복적인 과정이고, 처음부터 모든 것을 확장하는 것이 아니라 단계별로 필요한 부분을 확장해 나간다는 점이 인상 깊었다. 규모가 커질수록 점점 수평적인 규모 확장을 적용하면서 최종적인 구조로 변해가는 모습도 기대되었다.

## 면접 예상 질문

1. **Q. 수직적 확장과 수평적 확장의 차이는?**
   **A.** 수직적 확장은 서버 하나의 CPU나 RAM 같은 성능을 올리는 거고, 수평적 확장은 서버 자체를 여러 개로 늘리는 방식이다. 수직적 확장은 간단하지만 결국 성능에 한계가 있고, 서버 하나에 문제가 생기면 전체 서비스에도 문제가 생길 수 있다.

2. **Q. 로드밸런서는 왜 사용하는가?**
   **A.** 서버가 여러 개 있을 때 요청이 한 서버에만 몰리지 않도록 나눠주는 역할을 한다. 트래픽을 분산할 수 있고 서버 하나에 문제가 생겨도 다른 서버에서 요청을 처리할 수 있다는 장점이 있다.

3. **Q. 무상태 웹 계층은 왜 필요한가?**
   **A.** 웹 서버가 사용자의 상태를 직접 가지고 있으면 해당 사용자의 요청을 계속 같은 서버에서 처리해야 한다. 상태 정보를 별도로 저장하면 어떤 웹 서버에서도 요청을 처리할 수 있어서 서버를 여러 개로 확장하기 편해진다.

4. **Q. 캐시는 왜 사용하는가?**
   **A.** 자주 사용하는 데이터를 저장해두고 다시 사용해서 매번 DB에서 데이터를 가져오지 않도록 하기 위해 사용한다. 응답 속도를 높이고 DB의 부담을 줄일 수 있지만, 실제 데이터와 달라질 수 있기 때문에 만료 시점도 중요하다.
